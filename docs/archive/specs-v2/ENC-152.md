# ENC-152 — Page 404 et erreurs custom (cohérence brand)

## Objectif métier

Une erreur, c'est un moment de friction : c'est précisément là qu'il faut soigner l'expérience pour ne pas perdre le visiteur. Aujourd'hui, EnCave affiche le 404 par défaut Next.js (typo générique, pas de brand, pas de chemin de retour). On veut transformer ces moments en occasion de réorienter l'utilisateur avec le ton EnCave : empathique, jamais culpabilisant, sourire en filigrane.

## Acteurs

- CLIENT (principal) — visiteur public qui tombe sur un lien cassé, URL malformée, expérience archivée
- WINEMAKER (secondaire) — même chose côté dashboard (mais ton plus pro)

## Préconditions & déclencheurs

- Routes existantes Next.js : `not-found.tsx` (404), `error.tsx` (500 / runtime), `global-error.tsx` (root error boundary)
- Système de design Tailwind + shadcn/ui + font Manrope déjà en place
- Déclencheurs :
  - URL inconnue → 404
  - Erreur runtime serveur → 500 (`error.tsx`)
  - Erreur root layout → `global-error.tsx`

## User stories

> En tant que **visiteur** qui suit un lien partagé sur WhatsApp et tombe sur une expérience qui n'existe plus, je veux une page d'erreur sympathique qui m'oriente vers d'autres expériences proches, afin de ne pas quitter le site.

> En tant que **visiteur** qui rencontre une erreur serveur, je veux pouvoir réessayer en un clic ou retrouver mon chemin vers l'accueil, sans me sentir coupable de la panne.

## Règles métier

- **Pages à créer/refondre** :
  1. `src/app/[locale]/not-found.tsx` — 404 standard
  2. `src/app/[locale]/error.tsx` — erreur runtime route
  3. `src/app/global-error.tsx` — erreur root (sans layout, doit inclure `<html>` et `<body>`)
  4. (Optionnel) `src/app/maintenance/page.tsx` — page maintenance (cf questions ouvertes)

- **Comportement spécifique 404** :
  - Expérience archivée → 404 (vs 410 Gone, choix simple pour MVP)
  - Winery non VERIFIED accédée publiquement → 404
  - Booking inexistant → 404 (jamais révéler qu'il a existé)
  - Bloc suggestions : 3 expériences PUBLISHED aléatoires (réutiliser query existante listing)

- **Comportement spécifique 500** :
  - Toujours logger dans Sentry avec `digest` Next.js
  - Ne JAMAIS afficher le stack trace en prod
  - Bouton "Réessayer" appelle `reset()` (props de `error.tsx`)
  - En dev : afficher le message d'erreur (`process.env.NODE_ENV === 'development'`)

- **Branding visuel** :
  - Typo Manrope (cohérent app)
  - Couleurs charte EnCave (bordeaux primaire, ivoire fond)
  - Illustration légère : verre de vin renversé pour 404 (à arbitrer avec Léa, ou simple typo XXL en bordeaux)
  - Pas d'émoji dans le contenu permanent (cohérent règle email)
  - Touch target CTA ≥ 44px mobile

- **i18n** : tous textes via `getTranslations('Errors')`. Clés ajoutées dans `messages/fr.json`, `messages/de.json`, `messages/en.json`.

- **SEO** :
  - 404 : `<meta name="robots" content="noindex">` + statut HTTP 404
  - 500 : `noindex` + statut 500
  - Pas de canonical sur ces pages

## États UI

- **Loading** : pas de loading direct (404/500 sont synchrones). Le bloc suggestions peut être en `<Suspense>` avec un skeleton de 3 cards.
- **Empty** : si aucune expérience PUBLISHED disponible pour le bloc suggestions, masquer le bloc (pas d'état "empty" visible).
- **Error** : si la query suggestions échoue, masquer silencieusement le bloc (la page d'erreur ne doit pas elle-même casser).
- **Populated** : titre + sous-titre + CTAs + bloc suggestions (si dispo)

## Cas limites

- **Erreur dans `error.tsx` lui-même** : `global-error.tsx` prend le relai. Doit être minimaliste, sans dépendre du layout.
- **Erreur côté client (hydration mismatch)** : capturée par `error.tsx`. S'assurer que `'use client'` est posé.
- **404 en API route** : retourner `Response` JSON avec `{ error: 'not_found' }` et statut 404, pas un HTML. Périmètre API séparé.
- **Locale invalide dans l'URL** (`/zz/...`) : déjà gérée par next-intl middleware → redirect vers locale par défaut. Pas besoin de spécifique.
- **Bot crawler** : doit recevoir HTTP 404 explicitement (pas une 200 avec contenu "non trouvé") — sinon Google indexe. Vérifier `notFound()` Next.js retourne bien 404.
- **Lien partagé sur réseau social** : la 404 doit avoir un OG image générique EnCave (pas d'image cassée dans le preview WhatsApp/Twitter).
- **Maintenance** : si on l'inclut, la mettre en variable d'env (`MAINTENANCE_MODE=true`) lue par middleware qui short-circuit toutes les routes. Hors périmètre direct mais à prévoir.

- Design tokens Tailwind + shadcn/ui existants

## Hors-périmètre explicite

- **Pas** de page maintenance fonctionnelle (juste la copy si Sam le veut, mais le toggle côté infra/middleware est une autre US)
- **Pas** d'illustration custom complexe (au max une typo XXL ou un pictogramme léger)
- **Pas** de tracking événements PostHog sur ces pages (post-MVP)
- **Pas** de chatbot / formulaire de contact sur la 404 — un simple email suffit
- **Pas** de page 403 dédiée (les accès interdits redirigent vers signin)

## Métriques de succès

- 0 retour de la 404 Next.js par défaut sur n'importe quelle URL EnCave
- Bounce rate sur la page 404 < 60% (visiteurs qui cliquent un CTA)
- Toutes les 500 loguées dans Sentry avec digest exploitable
- 100% des textes traduits dans les 3 locales (validé par `npm run i18n:check`)
