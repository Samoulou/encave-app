# ENC-135 — Endpoint droit à l'oubli nLPD (anonymisation user + bookings)

## Objectif métier

Permettre à tout utilisateur (client ou encaveur) d'exercer son **droit à l'effacement** au sens de la nLPD (art. 32 al. 2 let. c). Le défi : on ne peut pas hard-delete les bookings (obligation comptable suisse de **conservation 10 ans** des pièces de vente — art. 958f CO + droit fiscal). Solution : **anonymisation** des données personnelles (PII) tout en préservant l'intégrité comptable et la cohérence référentielle. Bonus : se prémunir d'une demande légitime non honorée = sanction pénale individuelle jusqu'à 250'000 CHF (art. 60 nLPD).

## Acteurs

- **CLIENT** : déclenche la demande depuis ses paramètres `/settings/privacy/delete-account`. Reçoit confirmation email.
- **WINEMAKER** : peut aussi déclencher, **avec un cas particulier** : impossible si une winery active a des bookings futures. Doit d'abord transférer / archiver. (Cf. cas limites.)
- **ADMIN** : peut déclencher l'anonymisation à la demande (cas SAV : email envoyé par un client, ticket). Vue audit sur les anonymisations passées.
- **Système** : un job idempotent applique la transformation, log dans `AdminAction` (dépend ENC-126 P1).

## Préconditions & déclencheurs

- Trigger 1 : utilisateur authentifié → bouton "Supprimer mon compte" → confirmation par re-saisie email + mot de passe → server action → exécution synchrone (rapide, <2s) + signout.
- Trigger 2 : admin → écran admin user → bouton "Anonymiser cet utilisateur" → modale confirmation avec raison libre → log dans `AdminAction`.
- Préconditions bloquantes :
  - Encaveur avec ≥1 booking future `CONFIRMED` → refus, message dirigeant vers "annuler les events ou contacter le support".
  - Booking avec litige Stripe en cours (dispute ouverte) → refus, redirige vers support.

## User stories

- En tant que **client**, je veux pouvoir supprimer mon compte et faire effacer mes données personnelles, en 2 minutes, sans contacter le support.
- En tant que **encaveur**, je veux la même chose, mais sans casser mes obligations envers les clients qui ont une résa future.
- En tant que **admin**, je veux exécuter une demande légitime reçue par email et avoir une trace audit.
- En tant que **PO**, je veux être conforme à la nLPD ET au droit comptable suisse simultanément.

## Règles métier

- **Anonymisation ≠ suppression hard**. On garde les lignes, on retire les PII.
- **Données anonymisées sur `User`** :
  - `email` → `deleted-<cuid8>@encave.ch`
  - `name` → `"Utilisateur supprimé"`
  - `phone` → `null`
  - `image` → `null`
  - `cookieConsent` → `null`
  - `emailVerified` → `false`
  - `password` (Better Auth credential) → supprimé
  - Tous les `Account` OAuth liés → supprimés
  - Toutes les `Session` → révoquées
  - `anonymizedAt` → `now()`
- **Données anonymisées sur `Booking`** :
  - `guestEmail` → `deleted-<cuid8>@encave.ch` (utiliser le même cuid8 que l'user pour cohérence si user lié)
  - `guestName` → `"Utilisateur supprimé"`
  - `guestPhone` → `null`
  - `notes` (champ libre client) → `null`
- **Données préservées sur `Booking`** :
  - `reference` (ENC-XXXXXX), `totalAmount`, `commissionAmount`, `experienceId`, `slotDate`, `status`, `paymentIntentId`, `createdAt`, `completedAt`.
  - Justification : pièce comptable conservée 10 ans (art. 958f CO).
- **Stripe** : le `Customer` Stripe reste — Stripe est responsable de leur conformité côté paiements. On **n'appelle pas** `stripe.customers.del()`. On ne touche que l'enregistrement EnCave.
- **Winery** (cas encaveur anonymisé sans booking future) :
  - Si la winery a un historique commercial : on anonymise le compte user, on bascule la winery en `SUSPENDED`, on dépublie les experiences (`PUBLISHED` → `ARCHIVED`), mais on **conserve** la winery + historique commandes.
  - Si la winery est `PENDING` et n'a aucune commande : on peut hard-delete winery + experiences DRAFT.
- **Reviews / messages** (post-MVP) : à anonymiser de la même façon le moment venu.
- **Email pré-anonymisation** : envoyé **avant** la mutation. Contient un récap des données qui seront effacées et de celles qui resteront (transparence nLPD).
- **Délai** : exécution synchrone <2s. Pas de queue, pas de soft-pending. La nLPD attend "dans les meilleurs délais" — ici c'est immédiat.
- **Idempotence** : si `anonymizedAt != null`, no-op.
- **Audit** : entrée dans `AdminAction` (table prévue par ENC-126) si déclenché par admin, OU dans `UserAction` (à créer en sous-tâche ?) si déclenché par l'user. Garder a minima un log structuré Pino.

## États UI

- **Loading** : bouton en `pending` pendant l'action, modale verrouillée.
- **Empty** : N/A.
- **Error** : message clair pour chaque cas (résa futures, dispute, mauvais mot de passe). Reste sur la modale, pas de redirection.
- **Populated** : après succès → redirect immédiat vers `/` avec toast, sessions purgées, le user est délogué.

## Cas limites

- **User déjà anonymisé qui se reconnecte (impossible)** : ses sessions sont révoquées et son mot de passe supprimé, donc no-op.
- **Réinscription avec ancienne email** : autorisée, car l'email original n'est plus dans la table (remplacé par `deleted-xxx@encave.ch`). Pas de contrainte unique violée.
- **User anonymisé avec bookings futures `PENDING_PAYMENT`** : on annule ces bookings d'office avant anonymisation (transition `PENDING_PAYMENT` → `CANCELLED_BY_CLIENT`), pas de refund nécessaire (pas payé). Email d'annulation envoyé à l'encaveur.
- **Encaveur sole-owner d'une winery avec historique** : la winery passe en `SUSPENDED`, experiences → `ARCHIVED`. Le user est anonymisé. La winery reste, propriétaire anonymisé.
- **Backups & logs Sentry/Pino** : on documente dans la politique de confidentialité que les sauvegardes purgent au bout de 30 jours, et que les logs applicatifs masquent les emails (déjà fait via redaction Pino — à vérifier en sous-tâche).
- **PostHog** : on appelle `posthog.identify` avec un opt-out à l'anonymisation pour stopper toute capture future de cet `distinct_id`. Les events passés restent (pseudonymisés).
- **Resend** : pas d'API delete sur Resend. Les emails passés restent dans leurs logs (30j de rétention par défaut). À mentionner dans la politique de confidentialité.
- **Cuid collision sur `deleted-<cuid8>@encave.ch`** : extrêmement improbable, mais on vérifie l'unicité (re-roll si collision).

## Hors-périmètre explicite

- **Pas de période de grâce de 30 jours** "vous avez 30 jours pour revenir" — surcomplique pour un MVP, pas exigé par la nLPD.
- **Pas de hard-delete des bookings** — interdit par le droit comptable.
- **Pas d'appel à `stripe.customers.del`** — Stripe gère son propre cycle de vie.
- **Pas de suppression d'une winery active avec historique** — protection commerciale envers les clients passés.
- **Pas de tableau admin des anonymisations** au MVP (vu via `AdminAction` ou logs).

## Métriques de succès

- 100% des demandes traitées en <5 secondes (incluant l'envoi email).
- 0 régression sur l'historique comptable (audit DB : tous les `Booking` `COMPLETED` ont `reference`, `totalAmount`, `slotDate` intacts).
- Trace audit retrouvable pour 100% des anonymisations admin.
