# ENC-028 — Brancher l'envoi de `WelcomeEmail` au signup encaveur (template existe déjà)

## Objectif métier
Aujourd'hui un encaveur qui s'inscrit reçoit uniquement l'email de vérification Better Auth. Aucun message de bienvenue ne lui rappelle qui est EnCave, quelles sont les prochaines étapes, ni comment nous joindre. C'est mauvais pour la conversion onboarding (taux d'abandon entre signup et création expérience) et désincarné par rapport à la promesse "premium-décontracté" portée par Sam. Le template `WelcomeEmail` existe déjà côté React Email, il reste à le câbler.

## Acteurs
- **WINEMAKER** : reçoit l'email dans les minutes qui suivent son signup.

## Préconditions & déclencheurs
- Déclencheur : un nouvel utilisateur termine son signup avec le rôle `WINEMAKER` (et seulement ce rôle — pas les `CLIENT`).
- Hook Better Auth : `signUp` callback côté serveur ou listener sur la création User. Idempotent : un encaveur ne doit recevoir le WelcomeEmail qu'une seule fois.

## User stories
- En tant qu'**encaveur** qui vient de m'inscrire, je reçois un email de bienvenue clair qui me rappelle pourquoi je suis là et ce que je dois faire maintenant.
- En tant qu'équipe **EnCave**, je veux que ce premier contact incarne notre ton et oriente vers les 3 prochaines actions (KYC Stripe, profil cave, première expérience).

## Critères d'acceptation (Gherkin)

```gherkin
Fonctionnalité: Envoi du WelcomeEmail au signup encaveur

Scénario: Signup encaveur — email envoyé une fois
  Étant donné un visiteur qui complète /signup avec le rôle WINEMAKER
  Quand le compte est créé et l'email vérifié
  Alors un email "Bienvenue sur EnCave" est envoyé à l'adresse fournie
  Et l'envoi est tracé dans les logs avec un `correlationId`

Scénario: Signup client — pas de WelcomeEmail encaveur
  Étant donné un visiteur qui s'inscrit avec le rôle CLIENT
  Quand le compte est créé
  Alors aucun WelcomeEmail encaveur n'est envoyé

Scénario: Idempotence — pas de doublon
  Étant donné un encaveur qui a déjà reçu son WelcomeEmail
  Quand un événement déclencheur est rejoué (retry webhook, etc.)
  Alors aucun second email n'est envoyé

Scénario: Échec d'envoi Resend
  Étant donné Resend indisponible
  Quand on tente l'envoi
  Alors l'erreur est loggée via logError
  Et le signup n'est pas bloqué (l'utilisateur peut continuer son parcours)
  Et l'email sera retenté (cf. stratégie retry — voir question Sam)
```

## Règles métier

**Moment d'envoi** :
- Après vérification de l'adresse email (`emailVerified === true`), pas au moment du signup brut. Sinon l'encaveur reçoit le welcome avant même d'avoir cliqué sur le lien de vérification, c'est confusant.
- Implémentation : listener sur `user.update` quand `emailVerified` passe de `false` à `true` ET `user.role === 'WINEMAKER'`.

**Idempotence** :
- Ajouter un champ `welcomeEmailSentAt: DateTime?` sur `User` (ou table `EmailLog` si on prévoit d'autres lifecycle emails — cf. ENC-035 KYC relance). Recommandation Théo : table `EmailLog` simple `{ userId, kind, sentAt, providerMessageId }` pour mutualiser.
- Avant envoi : check `welcomeEmailSentAt == null`. Sinon skip + log info.

**Service** :
- Créer `src/server/services/welcome-email.service.ts` exposant `sendWelcomeEmailToWinemaker(userId)`.
- Récupère user, vérifie idempotence, appelle Resend avec le template existant, marque `welcomeEmailSentAt = now()`.
- Le service n'est pas appelé depuis un Server Component ni un middleware — il est appelé depuis un hook Better Auth (server-side, après vérif email).

**Contenu email** (template existe, à enrichir) :
- Sujet, salutation, mini-pitch EnCave (1 phrase), 3 prochaines étapes avec liens directs (KYC Stripe, profil cave, première expérience), signature équipe + lien direct Sam pour les Fondateurs.
- Le template actuel est-il déjà figé sur ce contenu ? **À vérifier** — cf. questions Sam.

**Internationalisation** :
- Locale envoyée = locale du user au moment du signup (`user.locale`, fallback `fr`).
- 3 versions FR/DE/EN dans `messages/{locale}.json` sous namespace `Emails.welcomeWinemaker`.

## États UI
N/A — c'est un email transactionnel, pas d'état UI applicatif. Néanmoins :
- **Loading** (côté service) : envoi asynchrone, le signup n'attend pas la réponse Resend.
- **Error** : log `logError` avec `correlationId`, le user n'est pas notifié visuellement de l'échec.
- **Sent** : `welcomeEmailSentAt` set, `providerMessageId` stocké pour debug.

## Cas limites
- **Email rebondit** (hard bounce Resend) : log warning, on ne retente pas automatiquement. Sam peut être notifié via dashboard admin (hors scope ici).
- **User change d'email avant vérification** : `welcomeEmailSentAt` toujours `null`, le welcome partira sur la nouvelle adresse au moment de la vérification.
- **User encaveur créé manuellement par admin** (cas Fondateur ajouté à la main par Sam) : doit aussi déclencher le welcome → on garde le trigger sur `emailVerified === true`, peu importe l'origine.
- **Locale mismatch** : si `user.locale` est manquant, fallback `fr` (locale par défaut).
- **Resend rate limit** : 429 → log + retry simple à J+1 (cf. ENC-035 qui aura sa propre logique de relance).

## Dépendances
- Template `WelcomeEmail` (React Email) — existe déjà selon le backlog, à valider.
- Better Auth hooks `signUp` / `user.update`.
- Resend (déjà câblé pour d'autres emails).
- Table `EmailLog` ou champ `welcomeEmailSentAt` — décision Sam.

## Hors-périmètre explicite
- Stratégie de retry sophistiquée (queue, exponential backoff) — un retry simple suffit MVP.
- Email de bienvenue pour les clients (rôle `CLIENT`) — à spécifier séparément si besoin.
- A/B testing du contenu.
- Tracking d'ouverture / clic (PostHog email events) — utile mais hors scope.

## Métriques de succès
- 100% des nouveaux encaveurs avec `emailVerified=true` ont `welcomeEmailSentAt` non-null sous 5 min.
- Taux d'ouverture > 70% (cible premium B2B).
- Taux de clic sur ≥ 1 CTA des 3 étapes > 40% (mesuré via UTM ou Resend events si activé plus tard).
