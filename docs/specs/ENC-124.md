# ENC-124 — Page admin liste événements (filtres statut + suspension manuelle)

## Objectif métier

Permettre à Sam (admin) de superviser l'ensemble des expériences publiées sur EnCave depuis un seul écran : trouver rapidement un événement signalé, vérifier son statut de publication, et le **suspendre** en cas de problème (contenu inapproprié, signalement client, encaveur en suspension). C'est la vue inverse du dashboard encaveur, côté plateforme. Indispensable pour modérer l'offre publique avant ouverture.

## Acteurs

- **ADMIN** uniquement (Sam).
- Indirectement : encaveurs (notifiés en cas de suspension de leur événement), clients ayant des bookings actives (politique à confirmer — cf questions Sam).

## Préconditions & déclencheurs

**Préconditions** :
- Utilisateur connecté, rôle `ADMIN`.
- Accès via `/admin/experiences` (route group `admin`).

**Déclencheurs** :
- Sam veut auditer le catalogue avant un événement marketing.
- Sam reçoit un signalement et cherche un événement par titre/cave.
- Routine de modération hebdomadaire.

## User stories

- En tant qu'admin, je veux voir la liste complète des expériences (toutes wineries, tous statuts) avec pagination.
- En tant qu'admin, je veux filtrer par statut (`DRAFT`, `PUBLISHED`, `ARCHIVED`, `SUSPENDED`), par winery, et par fenêtre de date (date du prochain créneau).
- En tant qu'admin, je veux rechercher une expérience par titre (recherche fuzzy/contains).
- En tant qu'admin, je veux suspendre une expérience publiée d'un clic, avec saisie d'une raison, pour la retirer immédiatement du public.
- En tant qu'admin, je veux réactiver une expérience suspendue (transition `SUSPENDED` → `PUBLISHED`).
- En tant qu'admin, je veux voir d'un coup d'œil le nombre de bookings futures associées à un événement avant de le suspendre.

## Critères d'acceptation (Gherkin)

```gherkin

  Quand j'arrive sur /admin/experiences
  Alors je vois les 20 premières (tri : updatedAt DESC)

  Alors l'URL devient /admin/experiences?status=PUBLISHED

Scénario : Recherche par titre

  Quand je tape "fendant" dans la recherche
  Alors la ligne correspondante est affichée
  Et la recherche est insensible à la casse et aux accents
```

## Règles métier

- **Nouveau statut `SUSPENDED` sur Experience** : à ajouter à l'enum `ExperienceStatus` (Prisma). Différent de `ARCHIVED` (qui est une action encaveur, irréversible côté UX encaveur). `SUSPENDED` est admin-only, réversible.
- **Transitions autorisées** :
  - `DRAFT` → `SUSPENDED` autorisé (rare mais possible, ex: contenu draft signalé).
  - `PUBLISHED` → `SUSPENDED` autorisé.
  - `SUSPENDED` → `PUBLISHED` (réactivation admin) autorisé.
  - `SUSPENDED` → `ARCHIVED` autorisé (l'admin peut archiver après suspension).
  - `ARCHIVED` → `SUSPENDED` interdit (déjà out de l'offre).
- **Effet sur visibilité publique** : une expérience `SUSPENDED` est exclue des queries publiques (listing `/decouvrir`, recherche, page winery publique). Page directe renvoie soit 404, soit une page "Cette expérience n'est plus disponible" (à trancher avec Léa).
- **Bookings existantes lors d'une suspension** : **conservées telles quelles**, **non annulées automatiquement**. La suspension est une action de **modération du listing**, pas une annulation événement. Si Sam veut annuler aussi les bookings, il le fait événement par événement via le détail booking + refund manuel (ENC-128) ou via l'annulation événement encaveur (ENC-045) qu'il peut déclencher à la place de l'encaveur (post-MVP).
- **Cas limite : suspendre tout en ayant des bookings actives** : warning à l'écran de confirmation "X bookings confirmées seront conservées. Pour annuler aussi les réservations, traite-les individuellement après suspension."
- **Filtres combinables** : statut + winery + dateRange + search peuvent coexister, encodés dans l'URL via `nuqs`.
- **Pagination** : 20 / page, paramètre `page` dans l'URL.
- **Tri par défaut** : `updatedAt DESC`. Tri secondaire possible par `createdAt`, `title` (post-MVP).
- **Logging** : suspension et réactivation logguées via AdminAction (ENC-126).
- **Cache** : suspension invalide les tags experience + listing public.

## États UI

- **Loading** : skeleton table (5-6 lignes grises) sur premier render. Spinner inline lors des filtres (Suspense boundary via `nuqs` + Server Component).
- **Empty** : `EmptyState` shared component avec titre "Aucune expérience" + texte "Aucune expérience ne correspond à tes filtres" + bouton "Réinitialiser les filtres".
- **Error** : `error.tsx` du segment avec message générique + bouton "Réessayer". Sentry log automatique.
- **Populated** : table avec lignes denses, badge coloré par statut (vert PUBLISHED, gris DRAFT, orange SUSPENDED, gris ARCHIVED), kebab menu actions à droite.

## Cas limites

- **Suspendre une expérience DRAFT** : autorisé mais redondant (déjà invisible publiquement). UX : warning "Cette expérience est en brouillon, déjà invisible publiquement. Suspendre quand même ?"
- **Winery elle-même suspendue (ENC-127)** : toutes ses expériences sont déjà invisibles publiquement (cf logique ENC-027 + ENC-127). Sam peut quand même suspendre l'expérience individuellement. Cohérent.
- **Recherche avec caractères spéciaux** : normalisation Unicode côté serveur (accents, espaces) pour matcher "Fendant" et "fëndant".
- **Filtres conflictuels** : statut = ARCHIVED + dateRange futur → liste vide (légitime, on affiche empty state).
- **Pagination + filtre** : changer un filtre reset `page` à 1.
- **Volume** : MVP < 200 expériences. Pas de virtual scrolling nécessaire.
- **Action sur expérience supprimée entre l'affichage et le clic** : server action vérifie l'existence, renvoie une erreur "Cette expérience n'existe plus" et invalide le cache liste.

## Dépendances

- **ENC-126** (AdminAction) : nécessaire pour logger suspend/unsuspend. À livrer avant.
- **ENC-125** (détail booking) : la colonne "Résa à venir" pointera vers `/admin/bookings?experienceId=...` (filtre à supporter dans ENC-125).
- **Migration Prisma** : ajout valeur `SUSPENDED` à l'enum `ExperienceStatus`. Penser à mettre à jour toutes les queries publiques qui filtraient `status: 'PUBLISHED'` pour s'assurer qu'elles excluent bien `SUSPENDED`.
- **`invalidateExperienceCaches`** : déjà existant (cf CLAUDE.md), réutiliser.
- **i18n** : 3 fichiers (`fr.json`, `de.json`, `en.json`) + `npm run i18n:check`.

## Hors-périmètre explicite

- Pas d'**édition admin** des champs d'une expérience (titre, prix, photos). Sam ne se substitue pas à l'encaveur.
- Pas de **suppression hard** depuis l'admin. Suspension/archivage suffit.
- Pas d'**annulation automatique des bookings** lors d'une suspension (workflow séparé, cf ENC-045 et ENC-128).
- Pas de **bulk actions** (suspendre 10 expériences d'un coup).
- Pas d'**export CSV** de la liste (post-MVP).
- Pas d'**historique des changements de statut** côté UI (l'historique est dans la table AdminAction, consultable plus tard).
- Pas de **filtre par tags / catégorie d'expérience** (post-MVP).

## Métriques de succès

- Temps moyen pour trouver une expérience par recherche : < 5s.
- Nombre de suspensions / mois (baseline ouverture publique).
- Taux de réactivation après suspension (qualité des décisions de modération).

## Questions ouvertes pour Sam

1. **Bookings actives lors d'une suspension** : on les **conserve** par défaut (politique recommandée ci-dessus). OK ? Ou tu préfères systématiquement déclencher un workflow d'annulation+refund de toutes les bookings futures lors d'une suspension ?
2. **Page publique d'une expérience suspendue** : 404 ou page dédiée "Cette expérience est temporairement indisponible" ? La 2e option est plus douce pour les liens partagés.
3. **Distinction `SUSPENDED` vs `ARCHIVED`** : on confirme que `SUSPENDED` est **admin-only et réversible**, et que `ARCHIVED` reste **encaveur-only et terminal** ? Cohérent avec ton modèle mental ?
4. **Filtre date** : on filtre sur "événement avec au moins un créneau dans la fenêtre" (logique `AvailabilitySlot` + `BlockedDate`) ou sur `createdAt` de l'expérience ? La 1ère est plus utile mais plus complexe.
