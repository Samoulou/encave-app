# ENC-153 — Loading states + skeleton UI sur pages lentes

## Objectif métier

Quand une page met >500ms à charger côté serveur (listings filtrés, dashboard encaveur avec stats, page winery riche en photos), un écran blanc fait paraître l'app cassée. Un skeleton UI bien posé communique "ça arrive, prends une seconde" et **réduit la perception de lenteur de 30-40%** (étude Nielsen Norman). Objectif : zéro écran blanc >300ms sur les pages publiques et dashboard.

## Acteurs

- CLIENT (principal) — visiteur mobile, parfois en 4G lente (train, montagne)
- WINEMAKER (principal) — dashboard avec listes de bookings, stats, calendrier

## Préconditions & déclencheurs

- Mesure préalable : identifier les pages avec TTFB > 500ms ou navigation transitoire perceptible
- Composant `Skeleton` shadcn/ui déjà disponible
- Mécanisme Next.js `loading.tsx` + `<Suspense>` exploitable
- Hook `useNavigateWithTransition` existant pour transitions client

## User stories

> En tant que **client** qui filtre les expériences par région, je veux voir un skeleton de cards (pas un écran blanc) pendant que les résultats chargent, afin de comprendre que ma recherche est en cours.

> En tant qu'**encaveur** qui ouvre son dashboard sur Android en 4G, je veux voir la structure de mes stats apparaître immédiatement avec des placeholders, afin de ne pas penser que l'app est plantée.

## Règles métier

- **Pages à traiter (priorisées par fréquence d'usage)** :
  1. `/[locale]/experiences` (listing public) — skeleton de N cards (N = limit query)
  2. `/[locale]/experiences/[winerySlug]/[experienceSlug]` (détail) — skeleton hero + bloc resa
  3. `/[locale]/wineries/[slug]` (page cave publique) — skeleton hero + grid expériences
  4. `/dashboard` (encaveur home) — skeleton 4 stat cards + liste prochaines résas
  5. `/dashboard/bookings` (encaveur liste résas) — skeleton table
  6. `/dashboard/experiences` (encaveur liste exp) — skeleton table
  7. `/admin/wineries` (admin modération) — skeleton table

- **Approches techniques** :
  - **`loading.tsx`** : utiliser pour les routes entières quand toute la page dépend du même fetch
  - **`<Suspense>`** + `loading.tsx` partiel : pour streamer des sections indépendantes (ex: stats dashboard qui chargent indépendamment de la liste résas)
  - **Skeleton client (état transitoire)** : pour filtres / mutations rapides via `useTransition` ou `nuqs` — afficher état `isPending`
  - Utiliser exclusivement le composant `Skeleton` de shadcn/ui (pas de div bricolée)

- **Design skeleton** :
  - Couleur : `bg-muted` shadcn (cohérent thème)
  - Animation : pulse (par défaut shadcn)
  - **Doit refléter la structure réelle** : un skeleton de card doit avoir les mêmes proportions que la card finale (évite CLS au remplacement)
  - Texte : barres horizontales de largeurs variées (~60-90%)
  - Images : carré ou rectangle de la bonne aspect ratio

- **Seuils de déclenchement** :
  - Skeleton visible si TTFB > 200ms (sinon transition trop rapide = flash gênant)
  - Skeleton minimum 300ms si affiché (sinon flash → considérer `useTransition` qui gère la délai naturellement)

- **Mesure perf à l'avant** (pour prioriser) :
  - Sentry Performance traces TTFB par route en prod
  - Pages avec p75 TTFB > 500ms = candidates principales
  - Procédure : lancer un run sur staging avec seed représentatif et noter les TTFB

## Copy FR définitive

Les skeletons ne contiennent pas de texte. Cependant, dans certains cas (chargements longs >3s, fallback API down), on peut afficher un message :

| Élément | Clé i18n suggérée | Texte FR |
|---|---|---|
| Loading prolongé (>3s) | `Loading.takingLonger` | "Le chargement prend un peu plus de temps que prévu…" |
| Filtres en cours | `Loading.filtering` | "Mise à jour des résultats…" |
| Aria-label skeleton (a11y) | `Loading.ariaLabel` | "Contenu en cours de chargement" |
| Dashboard stats loading | `Loading.dashboard.stats` | "Chargement des indicateurs…" |

> Le message "loading prolongé" est optionnel et apparaît seulement après 3s. Ne pas l'utiliser systématiquement (anxiogène).

## États UI

- **Loading** : c'est l'état principal. Skeleton qui reflète la structure finale.
- **Empty** : déjà géré par `EmptyState` shared component (hors périmètre, mais ne pas confondre).
- **Error** : si le fetch échoue après skeleton, transition vers état d'erreur (cf ENC-152 pour la copy, ici juste un message inline type "Impossible de charger ce contenu, réessayer ?").
- **Populated** : remplacement skeleton → contenu réel sans CLS.

## Cas limites

- **Skeleton qui ne matche pas le contenu final** : provoque un CLS visuel. Vérifier au pixel près les dimensions (utiliser screenshots de référence).
- **Suspense imbriqué** : si plusieurs Suspense streament en parallèle, l'ordre d'apparition doit être logique (haut → bas, ou hero → secondaire). Pas de pop aléatoire.
- **Cache hit** : pas de skeleton si la donnée est déjà en cache React (rendering synchrone). OK, c'est le comportement souhaité.
- **JS désactivé** : `loading.tsx` Next.js fonctionne sans JS (streaming SSR). Bonne propriété.
- **Slow client sur navigation** : `useTransition` rend la navigation non-bloquante mais peut donner une impression de "clic sans effet" si pas d'indicateur. Vérifier que `isPending` déclenche un état visuel.
- **Multi-skeleton sur une page** : ne pas multiplier les animations pulse (saturation visuelle). Maximum 2-3 zones de skeleton simultanées.
- **Locale switch** : pas besoin de skeleton (navigation rapide, géré par next-intl middleware).
- **Mode dégradé Sentry** : si Sentry est down, le skeleton ne doit pas durer indéfiniment (timeout côté query → fallback erreur).

## Dépendances

- Composant `Skeleton` shadcn (déjà installé)
- Hook `useNavigateWithTransition` existant
- Données Sentry Performance pour identifier les pages lentes (préalable à la priorisation)
- ENC-151 (audit Lighthouse) — feeds les bonnes pages à traiter

## Hors-périmètre explicite

- **Pas** d'optim back-end / DB index (autres tickets)
- **Pas** de skeleton sur pages auth (signin/signup, déjà rapides)
- **Pas** de skeleton sur modales (sauf si une modale lance un fetch lourd — pas le cas en MVP)
- **Pas** de stratégie SWR / revalidation custom — on garde l'approche RSC standard
- **Pas** d'animation de transition entre skeleton et contenu (fondu) — la simplicité shadcn suffit

## Métriques de succès

- 0 écran blanc > 300ms sur les 7 pages cibles (test manuel en Slow 3G simulé)
- CLS < 0.05 sur ces pages (pas de jump quand le skeleton est remplacé)
- 100% des routes lentes ont un `loading.tsx` ou un Suspense partiel
- Aucune régression Lighthouse Performance (≥ ENC-151)
