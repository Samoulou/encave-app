# ENC-013 — Reset password via magic link (Better Auth a la primitive, à câbler)

## Objectif métier
Un utilisateur (client comme encaveur) qui oublie son mot de passe doit pouvoir le réinitialiser sans contacter le support. Better Auth fournit déjà la primitive `requestPasswordReset` / `resetPassword` ; il reste à câbler l'UI (page "Mot de passe oublié" + page "Nouveau mot de passe") et l'email Resend. Sans ce flow, chaque oubli devient un ticket SAV — bloquant pour l'ouverture publique.

## Acteurs
- **CLIENT** : touriste/local qui a oublié son mot de passe.
- **WINEMAKER** : encaveur dans le même cas. Même flow, même UI (la page `/forgot-password` est commune aux deux rôles).
- **SYSTEM** : Better Auth + Resend, expéditeur du magic link.

## Préconditions & déclencheurs
- L'utilisateur a un compte EnCave actif avec email/password (pas un compte OAuth-only Google/Apple — cf. cas limite).
- Déclencheur : clic sur "Mot de passe oublié ?" depuis `/sign-in`.
- Better Auth ^1.4.17 expose `auth.api.requestPasswordReset({ email, redirectTo })` et `auth.api.resetPassword({ token, newPassword })`.
- Email transactionnel via Resend + template React Email.

## User stories
- En tant que **client**, j'ai oublié mon mot de passe ; je clique sur "Mot de passe oublié", je saisis mon email, je reçois un lien dans ma boîte, je clique, je définis un nouveau mot de passe et je suis automatiquement connecté(e).
- En tant qu'**utilisateur paranoïaque**, je ne veux pas qu'un attaquant puisse savoir si une adresse email a un compte EnCave en testant le formulaire.
- En tant que **plateforme**, je veux éviter que ce formulaire serve de canal de spam ou de brute-force d'emails.

## Critères d'acceptation (Gherkin)

```gherkin
Scénario : demande de reset pour un email existant
  Étant donné un compte avec l'email "marie@example.ch"
  Quand l'utilisateur soumet le formulaire /forgot-password avec "marie@example.ch"
  Alors un email "Réinitialisez votre mot de passe" est envoyé via Resend
  Et l'email contient un lien vers /reset-password?token=<jwt>
  Et le token expire 30 minutes après émission
  Et la page affiche le message générique de confirmation

Scénario : demande de reset pour un email inexistant
  Étant donné qu'aucun compte n'existe pour "fake@example.ch"
  Quand l'utilisateur soumet le formulaire avec "fake@example.ch"
  Alors aucun email n'est envoyé
  Et la page affiche EXACTEMENT le même message générique de confirmation
  Et la réponse HTTP a le même délai (~constant time) que pour un email valide

Scénario : reset password avec token valide
  Étant donné un token de reset émis il y a 5 minutes
  Quand l'utilisateur ouvre /reset-password?token=<jwt> et saisit un mot de passe valide
  Alors le mot de passe est mis à jour en base
  Et toutes les sessions actives de l'utilisateur sont révoquées
  Et l'utilisateur est connecté automatiquement avec une nouvelle session
  Et l'utilisateur est redirigé vers /account (client) ou /dashboard (winemaker) selon son rôle

Scénario : token expiré
  Étant donné un token émis il y a 31 minutes
  Quand l'utilisateur tente de l'utiliser
  Alors la page affiche "Ce lien a expiré"
  Et propose un CTA "Demander un nouveau lien"

Scénario : token déjà utilisé
  Étant donné un token utilisé avec succès il y a 2 minutes
  Quand l'utilisateur clique à nouveau sur le même lien
  Alors la page affiche "Ce lien n'est plus valide"
  Et propose un CTA "Demander un nouveau lien"

Scénario : compte OAuth-only (Google/Apple)
  Étant donné un compte créé uniquement via Google OAuth (pas de password en base)
  Quand l'utilisateur demande un reset pour cet email
  Alors aucun email de reset n'est envoyé
  Et la page affiche le message générique (pas de fuite d'info)
  Et un log warn est émis côté serveur pour observabilité

Scénario : rate limiting
  Étant donné 3 demandes de reset effectuées dans la dernière heure depuis la même IP
  Quand une 4ème demande arrive
  Alors la réponse est 429
  Et un message "Trop de tentatives, réessayez dans une heure" s'affiche

Scénario : mot de passe trop faible
  Étant donné un token de reset valide
  Quand l'utilisateur saisit "12345"
  Alors le formulaire affiche l'erreur de validation
  Et le mot de passe n'est pas modifié
```

## Règles métier
- **Expiration token : 30 minutes** à compter de l'émission. Stocké signé côté Better Auth (JWT ou table dédiée selon impl Better Auth — laisser Jonas trancher).
- **Non-révélation** : la page `/forgot-password` répond TOUJOURS le même message après submit, que l'email existe ou non. Pas de signal différenciant (status code, délai, redirect).
- **Time-constant response** : ajouter un délai aléatoire 200-400 ms côté serveur quand l'email n'existe pas pour égaliser le timing.
- **Comptes OAuth-only** : si l'utilisateur n'a pas de credential password en base (compte Google/Apple uniquement), on ne génère PAS de token et on n'envoie PAS d'email. Affichage générique côté UI.
- **Révocation sessions** : après reset réussi, invalider toutes les sessions actives Better Auth de cet utilisateur (sécurité). L'utilisateur sera connecté avec une nouvelle session post-reset.
- **Single-use token** : un token consommé devient invalide même s'il n'est pas expiré.
- **Rate limit** : 3 demandes / heure / IP **ET** 3 demandes / heure / email (double-clé). Utiliser la stack rate-limit existante (Upstash prod, in-memory dev — cf. `src/lib/rate-limit.ts` si présent).
- **Politique password** : mêmes règles que signup (min 8 caractères, à confirmer avec Sam si règle plus stricte). Validateur Zod réutilisé depuis `src/lib/validators/auth.ts`.
- **Magic link URL** : `https://encave.ch/{locale}/reset-password?token=<token>`. Locale = celle de l'utilisateur en base (pas celle du navigateur au moment de la demande).
- **Tracking** : log `logInfo` à la demande (sans révéler si email existe : log `email_hash`), log `logInfo` au reset réussi (avec userId).
- **Confirmation email post-reset** : envoyer un email "Votre mot de passe a été modifié" à toute adresse dont le password vient d'être changé (sécurité : permet à l'utilisateur de réagir si ce n'était pas lui).

## États UI

### Page `/forgot-password`
- **Loading** : bouton en état "Envoi en cours...", désactivé.
- **Empty** : formulaire vierge, focus sur le champ email.
- **Error** : message d'erreur sous le champ (validation Zod) ou bandeau rouge (rate limit).
- **Populated (succès)** : remplace le formulaire par une carte "Vérifiez votre boîte mail" avec icône enveloppe + texte succès générique + lien "Retour à la connexion". Pas de redirection auto.

### Page `/reset-password?token=...`
- **Loading initial** : skeleton pendant validation du token côté serveur.
- **Token valide** : formulaire 2 champs (password + confirm) + CTA.
- **Token expiré** : carte "Lien expiré" + CTA "Demander un nouveau lien" qui renvoie sur `/forgot-password`.
- **Token invalide / déjà utilisé** : même pattern que expiré, copy différente.
- **Submit loading** : bouton désactivé, label "Mise à jour...".
- **Succès** : toast + redirection vers `/account` (CLIENT) ou `/dashboard` (WINEMAKER) selon `session.user.role`.
- **Error submit** : erreur sous le formulaire, ne pas perdre la saisie.

## Cas limites
- Email avec espace en tête/queue → trim côté Zod avant lookup.
- Email casse mixte → comparaison case-insensitive (Better Auth doit déjà gérer).
- Utilisateur déjà connecté qui ouvre `/forgot-password` → laisser passer (cas valide : il veut changer le password sans connaître l'ancien). Alternative : Sam tranche s'il faut rediriger vers `/account/security`.
- Utilisateur déjà connecté qui clique sur un magic link → invalider la session courante avant de consommer le token, pour cohérence.
- Token avec un userId qui n'existe plus (compte supprimé entre émission et clic) → message "Ce lien n'est plus valide".
- Browser bloque les cookies tiers : le flow ne dépend pas de cookies tiers, OK.
- Email Resend bounce (adresse invalide) → log error côté serveur, l'utilisateur voit toujours le message générique côté UI (pas de fuite).
- Deux demandes successives (J+0, J+5min) : émettre 2 tokens, les 2 doivent fonctionner indépendamment ; le second n'invalide pas le premier. (À reconsidérer si Sam veut "dernier token gagne".)
- Email de l'utilisateur changé entre émission et clic → le token porte le userId, pas l'email ; il reste valide. OK.
- Compte SUSPENDED (admin a suspendu) → refuser le reset, message "Votre compte est suspendu. Contactez le support."

## Hors-périmètre explicite
- Pas de magic link "sign-in" (connexion sans mot de passe) — c'est ENC-014, reporté post-MVP.
- Pas de 2FA / TOTP.
- Pas d'historique des changements de password dans `/account/security`.
- Pas de policy d'expiration périodique forcée du password.
- Pas de vérification "ce password a déjà été utilisé".

## Métriques de succès
- 0 ticket SAV "j'ai oublié mon mot de passe" après mise en prod.
- Taux de complétion du flow (demande → reset effectif) > 60 %.
- 0 incident de fuite "email enumeration" remonté par audit sécurité.
