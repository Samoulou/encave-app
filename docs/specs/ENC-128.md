# ENC-128 — Action admin : refund manuel d'une booking + log

## Objectif métier

Donner à Sam (admin EnCave) un levier SAV pour rembourser manuellement une réservation en dehors de la règle standard (>24h = full, <24h = no refund). Indispensable pour gérer les cas particuliers : encaveur malade le jour J, client honnête de bonne foi, litige résolu à l'amiable, problème qualité signalé après l'expérience. Sans cet outil, chaque incident SAV obligerait à passer par le dashboard Stripe directement, sans cohérence avec l'état booking interne ni traçabilité côté plateforme.

## Acteurs

- **ADMIN** uniquement (Sam, et un éventuel assistant ADMIN futur).
- Le client est concerné indirectement : il reçoit un email de notification.
- L'encaveur est informé (email + impact reversement Stripe Connect via reversal du transfer).

## Préconditions & déclencheurs

**Préconditions** :
- L'utilisateur a le rôle `ADMIN` (vérifié via `await auth()` + check rôle dans server action).
- La booking existe et son `paymentStatus` est `SUCCEEDED` (paiement effectivement encaissé via Stripe).
- La booking n'a pas déjà été remboursée intégralement (`refundedAmountCents < paidAmountCents`).
- Le `PaymentIntent` Stripe associé est encore éligible au refund (généralement < 180 jours).

**Déclencheurs** :
- Sam ouvre le détail d'une réservation depuis `/admin/bookings/[reference]` (ENC-125) et clique sur "Rembourser".
- Sam reçoit un signalement client par email et veut traiter le cas SAV.

## User stories

- En tant qu'admin, je veux pouvoir rembourser tout ou partie d'une réservation pour gérer les cas SAV hors politique standard.
- En tant qu'admin, je veux saisir une raison obligatoire pour chaque refund manuel, afin de garder une trace auditable.
- En tant qu'admin, je veux voir l'historique des refunds déjà effectués sur une booking avant d'en faire un nouveau.
- En tant que client, je veux recevoir un email m'informant du remboursement, du montant exact et de la raison.
- En tant qu'encaveur, je veux être informé qu'un refund admin a été déclenché sur une de mes réservations.

## Règles métier

- **Override de la règle 24h** : ce refund admin ignore la règle standard. C'est sa raison d'être. La règle 24h ne s'applique qu'aux annulations client (ENC-045 côté encaveur).
- **Refund partiel autorisé** : Sam choisit entre "Remboursement intégral" ou "Montant personnalisé" (en CHF, converti en cents). Le montant personnalisé doit être ≤ `paidAmountCents - refundedAmountCents`.
- **Raison obligatoire** : champ texte libre, min 10 caractères, max 500. Stocké dans `AdminAction.reason`.
- **Transitions d'état booking** :
  - Refund **intégral** + booking en `CONFIRMED` ou `PENDING_PAYMENT` → `CANCELLED_BY_WINERY` (l'admin agit au nom de la plateforme/encaveur).
  - Refund **intégral** + booking en `COMPLETED` → reste `COMPLETED`, flag `refundedAmountCents` = total. On ne revient pas en arrière dans la state machine (cf CLAUDE.md "jamais en arrière").
  - Refund **partiel** → état booking **inchangé**, seul `refundedAmountCents` augmente.
  - Refund sur booking `NO_SHOW` → autorisé (cas rare : Sam estime que le no-show n'est pas la faute du client), reste `NO_SHOW`, refund tracé.
- **Stripe** : utiliser `stripe.refunds.create({ payment_intent, amount, reverse_transfer: true, refund_application_fee: true })` pour récupérer la commission plateforme **et** reverser depuis le compte Connect de l'encaveur. Source : `getStripe()` de `src/server/stripe.ts`.
- **Idempotence** : utiliser un `idempotencyKey` dérivé de `bookingId + currentRefundedAmount` pour éviter les doubles refunds en cas de double-clic.
- **Capacité événement** : si la booking passe à `CANCELLED_BY_WINERY`, libérer les places (logique existante).
- **AdminAction associée** : créée systématiquement (cf ENC-126), même en cas d'échec Stripe (status = FAILED dans metadata).
- **Notification client** : email immédiat (`Resend`), avec montant exact, raison (vulgarisée — voir copy), délai de réapparition fonds (5-10j ouvrés).
- **Notification encaveur** : email immédiat, montant impacté sur ses revenus, raison.
- **Pas de refund client-side** : seul `/admin` peut déclencher cette action (vs annulation client en self-service qui suit la règle 24h).

## États UI

- **Loading** : bouton "Rembourser" → spinner inline pendant la mutation Stripe (peut prendre 2-5s). Dialog désactivée, on bloque la fermeture pendant le call.
- **Empty** : section "Historique des remboursements" → cachée si aucun refund. Pas d'EmptyState explicite.
- **Error** : 
  - Échec Stripe : toast destructive + AdminAction loggée en FAILED. Dialog reste ouverte pour permettre de retry.
  - Raison < 10 char : erreur inline sous le textarea, bouton confirmer désactivé.
  - Montant invalide : erreur inline.
- **Populated** : carte "Paiement" du détail booking montre : montant payé, montant remboursé (si > 0), bouton "Rembourser" actif/désactivé. Sous-section "Historique des remboursements" liste chaque refund (date, montant, admin, raison).

## Cas limites

- **Double-clic / soumissions concurrentes** : idempotency key Stripe + lock applicatif sur `bookingId` pendant la mutation.
- **Booking en `PENDING_PAYMENT`** : pas de refund possible (aucun paiement n'est encore tombé) — bouton désactivé avec label "Paiement non encore confirmé".
- **PaymentIntent expiré (>180j)** : Stripe renvoie une erreur. On la trap, on log AdminAction en FAILED, on suggère à Sam de faire un virement manuel (out of scope plateforme).
- **Compte Connect encaveur fermé/suspendu** : le `reverse_transfer` peut échouer. Idem : erreur claire, fallback documenté.
- **Refund cumulatif dépassant le montant payé** : validation Zod côté serveur, refusé.
- **Client supprimé (RGPD/nLPD ENC-135)** : booking conservée anonymisée. Le refund reste possible (Stripe a son propre PII). Pas d'email envoyé (email anonymisé), juste log AdminAction.
- **Encaveur supprimé** : idem, refund possible, pas d'email encaveur.
- **Booking déjà `CANCELLED_BY_CLIENT`** : si paiement non encore refundé (cas rare : annulation hors-policy traitée manuellement), refund possible.
- **Devise multi-currency** : MVP = CHF uniquement, pas de cas à gérer.

## Hors-périmètre explicite

- Pas de refund **batch** (plusieurs bookings d'un coup). Cas par cas.
- Pas de **calculateur "refund recommandé"** basé sur la règle 24h. L'admin décide librement.
- Pas de **workflow d'approbation à 2** (Sam est seul admin pour MVP).
- Pas d'**export comptable** des refunds (post-MVP).
- Pas de **refund automatisé** sur base de règles complexes (annulation événement entier = ENC-045, c'est un workflow différent).
- Pas de **réversion d'état** booking en arrière (COMPLETED reste COMPLETED même si refund total).
- Pas de **modification de la raison** après coup. La raison est immuable une fois loggée.

## Métriques de succès

- Nombre de refunds manuels / mois (idéalement < 5% des bookings).
- Délai moyen entre signalement client et refund effectué (cible : < 24h).
- Taux d'échec Stripe (cible : < 2%).
