# ENC-134 — Mention 18+ sur pages event + checkout (obligation alcool Suisse)

## Objectif métier
Respecter l'obligation suisse de ne pas promouvoir/vendre d'alcool à des mineurs, tout en gardant une UX consistante "18+ partout" (plus simple à expliquer aux encaveurs que la double règle 16/18 par canton et par produit). Objectif secondaire : assumer un signal de **sérieux** pour les encaveurs et la presse, sans dégrader la conversion checkout par une friction inutile.

## Acteurs
- **CLIENT** : voit une mention discrète sur les pages event publiques, doit confirmer sur ses propres épaules son âge au checkout.
- **WINEMAKER** : aucun changement de flow ; mention "18+" affichée automatiquement sur ses experiences publiées.
- **ADMIN** : pas d'action.

## Préconditions & déclencheurs
- Toute page de détail d'une experience publiée (`/experiences/[winery]/[experience]`) : mention statique visible.
- Toute page de checkout / récap avant paiement Stripe : case à cocher obligatoire avant le bouton "Payer".
- Le check est strictement déclaratif (pas de KYC client). Pas d'âge gate modal au premier chargement.

## User stories
- En tant que **client**, je vois immédiatement que c'est une expérience adulte sans qu'on me bloque l'accès.
- En tant que **client** au checkout, je confirme explicitement que j'ai 18 ans avant de payer.
- En tant que **encaveur**, je n'ai rien à activer ni paramétrer : c'est appliqué partout.
- En tant que **PO**, j'ai trace que chaque booking confirmée a inclus un consentement âge (booléen + horodatage côté DB).

## Critères d'acceptation (Gherkin)

```gherkin
Fonctionnalité: Mention et confirmation d'âge 18+

Scénario: Mention discrète sur la page event
  Étant donné une experience publiée
  Quand un visiteur (connecté ou non) ouvre la page détail
  Alors un badge "Réservé aux 18+" est visible dans le bloc d'infos pratiques
  Et la page reste entièrement accessible (pas de modale bloquante)

Scénario: Case obligatoire au checkout
  Étant donné un client sur la page récap avant paiement
  Quand la case "Je certifie avoir 18 ans révolus" n'est pas cochée
  Alors le bouton "Payer" est désactivé

Scénario: Validation et persistance
  Étant donné un client qui coche la case et clique sur "Payer"
  Quand la booking passe en PENDING_PAYMENT
  Alors le champ Booking.ageConfirmedAt est rempli avec l'horodatage UTC
  Et le champ Booking.ageConfirmedVersion est rempli avec AGE_GATE_VERSION

Scénario: Tentative de bypass via Stripe direct
  Étant donné un client qui contourne le front et appelle l'action createCheckoutSession sans le flag
  Quand la server action valide la requête
  Alors elle retourne { ok: false, error: "AGE_CONFIRMATION_REQUIRED" }
  Et aucune session Stripe n'est créée

Scénario: Page archivée ou non publiée
  Étant donné une experience en DRAFT
  Quand on l'affiche en preview encaveur
  Alors le badge 18+ est tout de même visible (cohérence visuelle)

Scénario: Email de confirmation
  Étant donné une booking confirmée
  Quand l'email de confirmation est envoyé
  Alors il contient le rappel "Expérience réservée aux 18+. Une pièce d'identité pourra être demandée à l'arrivée."
```

## Règles métier
- **18+ partout**, pas de variation par canton ni par produit. Simple, défendable, et au-dessus de la loi minimale → safe.
- Mention page event = **badge informatif**, pas un gate. Pas de modale "Avez-vous 18 ans ?" sur la home ou les listings : friction stérile, pénalisante SEO/conversion.
- Mention au checkout = **case à cocher obligatoire**, **non pré-cochée** (sinon valeur juridique nulle en CH/EU).
- La case est sur la dernière étape avant Stripe (pas avant). Wording neutre, vouvoiement, sans accusation.
- Le serveur **doit revérifier** la présence du flag dans la server action `createCheckoutSession` (Zod schema). Ne pas se reposer sur le bouton désactivé côté client.
- Stockage : `Booking.ageConfirmedAt DateTime?` + `Booking.ageConfirmedVersion String?`. Versioning permet de re-flagger si le wording légal change.
- Email de confirmation reprend la mention 18+ + rappel ID — sert de pièce écrite si litige à l'arrivée.
- Page mentions légales (ENC-132b) doit lister la politique d'âge.

Ton : factuel, vouvoiement, jamais culpabilisant. Pas d'émoji, pas de pictogramme « interdit aux moins de 18 » trop strident — un simple badge texte suffit, design propre.

## États UI
- **Loading** : le badge est statique, rendu côté serveur, pas de loading.
- **Empty** : N/A — le badge s'affiche toujours sur les pages event.
- **Error** : si la case checkout est non cochée et que l'utilisateur clique "Payer" via DevTools (forçage), retour serveur → message d'erreur en haut du formulaire + scroll vers la case + focus dessus.
- **Populated** : badge bien visible dans la sidebar/infos pratiques de la page event ; case + helper sous le récap au checkout, juste au-dessus du bouton Payer.

## Cas limites
- **Mineur honnête qui coche quand même** : on n'a pas de moyen de vérifier en ligne ; la responsabilité bascule sur le client (déclaration) puis sur l'encaveur (contrôle ID à l'arrivée). Documenter dans les mentions légales.
- **Booking offerte / invitation +1** (ENC-083 à venir) : la confirmation est faite par le payeur principal. L'invité reçoit l'email avec le rappel 18+ mais ne re-confirme pas (pas de re-checkout). À noter pour quand ENC-083 sera spécifié.
- **Modification d'une booking** : si l'utilisateur modifie sa réservation (ex : changement de créneau futur), pas besoin de re-confirmer l'âge si `ageConfirmedVersion` est encore courant.
- **Bypass URL paiement direct (deeplink Stripe)** : impossible, on passe toujours par `createCheckoutSession` côté serveur, qui exige le flag.
- **A11y** : la case à cocher doit avoir un `aria-required="true"` et un message d'erreur lié via `aria-describedby`.

## Dépendances
- Migration Prisma : `Booking.ageConfirmedAt DateTime?` + `Booking.ageConfirmedVersion String?`.
- Constante `AGE_GATE_VERSION` dans `src/lib/constants/`.
- Validator Zod du checkout (`src/lib/validators/checkout.ts`) : ajouter `ageConfirmed: z.literal(true)`.
- Server action `createCheckoutSession` : check serveur + persistance des champs sur la booking créée.
- Template email confirmation : ajouter le bloc de rappel.
- Coordonner avec ENC-132b pour la politique alcool dans les mentions légales.

## Hors-périmètre explicite
- **Pas de KYC ID en ligne** (Onfido, Veriff, etc.) — disproportionné pour un MVP.
- **Pas de modale gate au premier chargement** sur la home ou les listings — friction stérile sur SEO et conversion.
- **Pas de différenciation par canton** ni par type de boisson.
- **Pas de blocage par date de naissance déclarative** — on ne demande pas la DDN dans le profil au MVP (donnée sensible inutile).
- **Pas de re-confirmation à chaque booking** d'un même user… mais en fait si, on re-confirme à chaque booking : c'est la trace écrite par booking qui a valeur juridique. À garder explicite.

## Métriques de succès
- 100% des bookings `CONFIRMED` ont `ageConfirmedAt != null` (audit DB hebdomadaire).
- Pas de pic de drop-off à l'étape checkout après mise en prod (comparer 7j avant/après, tolérance ±2 pts).
