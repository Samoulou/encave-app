# ENC-101 — Endpoint check-in (`checkedInAt` + transition CONFIRMED → COMPLETED via scan)

## Objectif métier
Fournir le server action atomique qui, à partir d'un token de booking (scanné ou cliqué manuellement), valide les autorisations, vérifie l'état, écrit `checkedInAt`, transitionne le booking vers `COMPLETED` et renvoie un retour exploitable par l'UI (scan QR ENC-100 + check-in manuel ENC-102). C'est la colonne vertébrale du jour-J.

## Acteurs
- **WINEMAKER** (déclencheur via UI scan ou manuel) : doit être propriétaire de la winery liée au booking.
- **CLIENT** : sujet passif (son booking change d'état). Reçoit éventuellement un email post-event (hors scope cette US).
- **ADMIN** : pas concerné ici (l'admin a son propre flux refund/SAV).

## Préconditions & déclencheurs
- Migration Prisma : ajouter `checkedInAt: DateTime?` sur `Booking` (nullable). Index non requis MVP.
- Server action `checkInBooking(input)` dans `src/server/actions/bookings/checkInBooking.ts`.
- Input : `{ token: string, expectedSessionId?: string }` (token = clair, hashé côté serveur avant lookup) OU `{ bookingId: string }` pour check-in manuel.
- Déclencheurs : ENC-100 (scan QR), ENC-102 (check-in manuel).

## User stories
- En tant qu'**encaveur**, je veux qu'un seul appel atomique valide tout (auth, ownership, état booking, fenêtre temporelle) et passe le booking à `COMPLETED`, afin de garantir la cohérence et d'éviter les doubles check-in.
- En tant que **dev**, je veux un endpoint idempotent : rejouer le même scan ne crée pas d'incohérence, retourne juste "déjà check-in".

## Règles métier
- **Transition autorisée** : `CONFIRMED → COMPLETED` uniquement. Aucune autre transition n'est faite par cette action.
- **Idempotence** : si `status === COMPLETED && checkedInAt !== null`, retourner `ALREADY_CHECKED_IN` sans modif.
- **Ownership** : `Booking.experience.winery.ownerId === session.user.id`.
- **Token lookup** : hasher le token clair (SHA-256, déjà la convention `accessTokenHash` dans CLAUDE.md) puis `findUnique({ where: { accessTokenHash } })`.
- **Atomicité** : transaction Prisma `$transaction` autour de check état + update.
- **Audit** : log `logInfo({ action: 'check_in', bookingRef, encaveurId, source: 'scan'|'manual' })` après succès.
- **Cache** : `revalidateTag(`event:${experienceSlug}`)` et `revalidateTag(`booking:${bookingId}`)` après update. Pas de `revalidatePath` ici.
- **Rate limit** : 30 check-in / minute par encaveur (anti-bruteforce token). Utilise la couche rate-limit existante.
- **Pas d'email** : aucun email transactionnel envoyé lors du check-in (post-event ENC-069/follow-up séparé).
- **Annuler un check-in** (`COMPLETED → CONFIRMED`) : fonctionnalité exposée dans ENC-096 mais implémentée dans une action sœur `undoCheckInBooking` (hors-scope strict de cette US — voir questions ouvertes).

## Cas limites
- **Token collision (très improbable, SHA-256)** : prendre le booking dont l'expérience appartient à l'encaveur authentifié si plusieurs résultats. Si toujours plusieurs : log Sentry error + `INTERNAL_ERROR`.
- **Booking lié à une session annulée par l'encaveur** (ENC-045) : `BOOKING_CANCELLED` (à ce stade le statut booking doit être `CANCELLED_BY_WINERY`).
- **Race condition double-scan simultané** : transaction Prisma sérialise, le second appel reçoit `ALREADY_CHECKED_IN`.
- **Booking dont l'experience est `ARCHIVED`** : on autorise quand même le check-in (cas legacy, un événement peut être archivé sans annuler ses bookings actifs). À discuter, voir questions ouvertes.
- **Migration Prisma** : déployer `checkedInAt` (nullable) sans backfill. Bookings COMPLETED antérieurs garderont `null` (pas grave, UI affiche "Présent" sans heure).
