# ENC-145 — Tests de charge basiques (200 résas/heure simulées)

## Objectif métier

Avant la bêta Fondateurs, on doit avoir la conviction que la plateforme tient une charge réaliste de **200 réservations/heure** sans dégradation (5xx, timeouts, DB saturée). Cette cible correspond à un scénario de pic plausible : une grande cave qui pousse une promo sur Instagram + saison vendanges + tunnel partagé via WhatsApp. En dessous de ce cap, on découvrirait la panne en prod. Le but n'est pas de stress-tester jusqu'à breakpoint, mais de **valider la cible MVP** et identifier les goulots évidents (pool DB, latence Stripe, cache).

## Acteurs

- CLIENT (simulé) — création booking + checkout
- Système (infra) — Vercel functions, Neon Postgres, Stripe, Resend
- Équipe dev (interne) — pilotage du test, lecture des métriques

## Préconditions & déclencheurs

- Environnement Staging (`encave-dev.vercel.app`) ou env dédié `loadtest` (préférable pour isoler de la démo)
- Neon `development` ou branche `loadtest` (créer si besoin pour ne pas polluer staging)
- Stripe en mode test (clés test) — pas de coût réel
- Outil de charge installé : **k6** ou **Artillery** (cf questions ouvertes)
- Seed représentatif : ≥ 10 wineries VERIFIED, ≥ 30 expériences PUBLISHED avec créneaux dispo
- Déclencheur : audit ponctuel pré-bêta. Pas de run continu.

## User stories

> En tant qu'**équipe produit**, je veux savoir si EnCave tient 200 bookings/h sans dégradation, afin de ne pas découvrir un goulot en bêta Fondateurs.

> En tant que **dev**, je veux un rapport listant les routes lentes sous charge, afin de prioriser des optims ciblées avant ouverture publique.

## Règles métier

- **Cible de charge** :
  - **200 bookings/h** = arrivée Poisson de ~3.3 bookings/min (réaliste pour un pic)
  - Durée du run : **30 min** minimum (capter le steady state, hors warm-up)
  - Ramp-up : 0 → 200/h sur 2 min
  - Modèle de charge : `constant-arrival-rate` k6 ou équivalent Artillery

- **Scénario fonctionnel par VU** (Virtual User) :
  1. `GET /fr/experiences` (listing public)
  2. `GET /fr/experiences/[winerySlug]/[experienceSlug]` (détail aléatoire dans le pool seed)
  3. `POST /api/bookings/create` ou action server équivalent → crée booking `PENDING_PAYMENT`
  4. `POST /api/checkout/create-session` → session Stripe Checkout test
  5. Simuler webhook `payment_intent.succeeded` via Stripe CLI ou injection directe en test → booking `CONFIRMED`
  6. (Optionnel) `GET /bookings/[ref]/confirmation` (lecture finale)

- **Pondération du trafic** (ratio réaliste) :
  - 70% des VU font uniquement parcours lecture (1+2), pas de booking
  - 30% des VU vont jusqu'au booking confirmé
  - Cible 200 bookings/h ≈ 670 VU/h en arrivée totale

- **Seuils de succès** (validation = tous verts) :
  | Métrique | Seuil |
  |---|---|
  | Taux erreurs 5xx | < 0.5% |
  | Latence p95 (chaque route) | < 1000ms |
  | Latence p99 | < 2500ms |
  | Taux de timeout (>10s) | 0 |
  | Saturation pool Neon | < 80% pic |
  | Saturation CPU Vercel function | < 70% pic |
  | Webhook handler p95 | < 500ms |
  | Cohérence DB (pas de double-booking, pas de PENDING_PAYMENT orphelin) | 100% |

- **Outils** :
  - **k6** (recommandé Théo) : open-source, scripting JS, métriques claires, intégration Grafana possible
  - **Artillery** : alternative Node, plus simple à scripter mais moins puissant en reporting
  - Lancement depuis machine locale (latence Suisse → Vercel correcte) ou GitHub Actions
  - Données à archiver : rapport HTML/JSON dans `docs/audits/loadtest-2026-XX/`

- **Mesure côté infra** :
  - Sentry Performance : trace par endpoint pendant le run
  - Vercel Analytics : invocations, latency, errors
  - Neon dashboard : connexions actives, CPU, IOPS
  - Stripe Dashboard : webhooks success rate

- **Garde-fous (à respecter pendant le run)** :
  - Run sur env **loadtest** ou **staging hors démo** uniquement
  - Stripe en mode test (jamais live)
  - Pas d'envoi email réel : mocker Resend ou utiliser un Resend test mailbox
  - Pas de notifications réelles aux encaveurs seed
  - Données seed dédiées, taggées (ex: email `loadtest+xxx@encave.ch`)

## Cas limites

- **Capacité limitée → race conditions** : 50 VU réservant le même créneau de capacité 10 doit produire exactement 10 succès. Si plus → bug de transaction. Vérifier que la création booking utilise une transaction Prisma avec un SELECT FOR UPDATE ou équivalent atomique.
- **Cold start Vercel** : peut fausser le p99. Faire un warm-up de 2 min avant la mesure officielle.
- **Stripe rate limits** : Stripe limite à ~100 req/s pour les requêtes write. 200 bookings/h = ~3.3/min, on est très loin. OK.
- **Neon connexion pool** : Prisma pooler côté `DATABASE_URL`. Vérifier que pgbouncer est actif (sinon saturation rapide).
- **PostHog + Sentry** : peuvent générer beaucoup d'events. Vérifier qu'ils n'ajoutent pas de latence bloquante (call sync vs async).
- **Idempotence webhook (ENC-030b)** : critique sous charge. Le test doit envoyer 2x le même event et vérifier qu'un seul booking est confirmé.
- **Emails Resend** : sous le seuil free tier 100/jour si run prod, attention. Préférer mock pour le test.
- **Cron expiration `PENDING_PAYMENT`** (ENC-067) : pendant le run, ne pas lancer le cron pour éviter pollution. Désactiver temporairement ou laisser tourner si run >30min.
- **Coût Neon** : 30 min de charge sur Neon dev coûte peu, mais si on monte à 1000/h c'est différent. Garder cible 200.

## Dépendances

- ENC-030b (idempotence webhooks Stripe) — sans ça, le test révélera des doubles confirmations légitimes mais on ne saura pas distinguer du bug
- ENC-067 (cron expiration PENDING_PAYMENT) — comportement à connaître
- Seed loadtest dédié à préparer (≥ 30 expériences avec créneaux et capacités variés)
- Branche Neon `loadtest` créée (recommandé)

## Hors-périmètre explicite

- **Pas** de stress test jusqu'au breakpoint (500/h, 1000/h, etc.) — post-MVP si besoin
- **Pas** de test de soak (24h continu) — post-MVP
- **Pas** d'optim incluse dans cette US — les fixes sont en tickets séparés
- **Pas** de test de charge sur dashboard encaveur (faible volume attendu)
- **Pas** de monitoring continu post-test — le rapport est un instantané
- **Pas** de DDoS / sécurité réseau (autre périmètre)

## Métriques de succès

- 200 bookings/h pendant 30 min avec **tous les seuils respectés** = US livrée
- Si un seuil dépasse, l'US livre **un rapport explicite** + tickets correctifs prioritisés (P0 si latence > 2× cible, P1 sinon)
- Reproductibilité : le script doit être ré-exécutable post-correctifs pour valider
