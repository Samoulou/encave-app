# ENC-096 — Page détail événement encaveur (liste des inscrits par session + actions)

## Objectif métier
Offrir à l'encaveur une vue opérationnelle complète d'un événement publié : qui est inscrit, sur quelle session, et quelles actions jour-J sont possibles (check-in, no-show, contact). C'est l'écran central du jour-J et le hub d'où partent ENC-100/102/103b.

## Acteurs
- **WINEMAKER** (acteur principal) : consulte sa page, déclenche les actions opérationnelles.
- **CLIENT** : présent en lecture indirecte (nom, +1, statut booking).
- **ADMIN** : pas concerné ici (admin a sa propre vue, hors-scope).

## Préconditions & déclencheurs
- L'encaveur est authentifié (`await auth()`) et propriétaire de la winery rattachée à l'événement (`winery.ownerId === session.user.id`).
- L'événement existe et n'est pas `ARCHIVED` (mais peut être `DRAFT` ou `PUBLISHED`).
- Déclencheur : clic depuis le dashboard ou l'agenda sur un événement, ou accès direct par URL.

## User stories
- En tant qu'**encaveur**, je veux voir tous les clients inscrits à mon événement, regroupés par session (date + heure), afin de préparer l'accueil du jour-J.
- En tant qu'**encaveur**, je veux pouvoir lancer un scan QR, marquer un client check-in manuellement ou no-show depuis cette page, afin de gérer la présence sans changer d'écran.
- En tant qu'**encaveur**, je veux voir d'un coup d'œil le remplissage de chaque session (X/Y places), afin de savoir où j'en suis commercialement.

## Règles métier
- **Tri sessions** : à venir d'abord (chrono croissant), puis "Aujourd'hui" mis en exergue, puis passées (repliées).
- **Comptage capacité** : `placesConfirmées = bookings où status ∈ {CONFIRMED, COMPLETED}`. NO_SHOW reste compté dans confirmé (la place a été vendue). CANCELLED_* ne sont pas comptés.
- **Affichage des bookings** : par session, tri par `createdAt` croissant (premier inscrit en haut).
- **Données par ligne booking** : nom client, email (cliquable mailto), nombre de personnes (`partySize`), référence `ENC-XXXXXX`, statut, heure de check-in si présente.
- **Actions disponibles par booking** :
  - `CONFIRMED` & session du jour : "Marquer présent" (manuel, ENC-102) + "Marquer no-show" (ENC-103b)
  - `COMPLETED` : badge "Présent à HH:MM" + bouton "Annuler le check-in" (revient à CONFIRMED, voir ENC-101 questions ouvertes)
  - `NO_SHOW` : badge no-show + bouton "Annuler le no-show" (revient à CONFIRMED)
  - `CANCELLED_*` : ligne grisée, pas d'action
- **Bouton scan QR** : visible uniquement sur sessions du jour ou à venir dans les 2h (anti-erreur). Renvoie vers `/dashboard/scan?experienceSlug=...&sessionId=...` (ENC-100).
- **Pré-filtre `sessionId`** : si plusieurs sessions le même jour, le scan préselectionne la session si l'encaveur arrive depuis cette session.
- **Accès** : action server `await auth()` + check `winery.ownerId === session.user.id`. Sinon → `redirect('/dashboard')`.

## États UI
- **Loading** : skeleton page (header + 3 cards session avec lignes grises). Utiliser `loading.tsx` au niveau route.
- **Empty (aucune session)** : `EmptyState` "Vous n'avez pas encore programmé de sessions" + CTA "Ajouter une session" (lien vers édition événement).
- **Empty (session sans inscrit)** : ligne inline "Aucune réservation pour cette session".
- **Error** : `error.tsx` au niveau route avec bouton "Réessayer".
- **Populated** : header événement + sections session triées + tableau bookings par session.

## Cas limites
- **Événement DRAFT** : la page reste accessible mais bannière "Cet événement n'est pas publié. Aucun client ne peut le voir." + scan QR caché.
- **Événement ARCHIVED** : lecture seule, aucune action disponible, bannière "Événement archivé".
- **Session annulée par encaveur (via ENC-045)** : section "Sessions annulées" séparée, lignes en gris, lien vers détail refund.
- **Capacité dépassée (≥ capacité)** : badge "Complet" sur la session.
- **Encaveur sans winery VERIFIED** : ne devrait pas pouvoir y arriver (l'événement n'existe pas). Si edge case : redirect dashboard.
- **Plus de 50 inscrits sur une session** : tableau scrollable verticalement, pagination interne à 50 (lazy load suite si > 50). MVP : on assume ≤ 50, on traite le surplus en P1.
- **Mobile** : tableau passe en cartes empilées (mobile-first), boutons d'action en bottom sheet.

## Décisions actées (Margot, 2026-05-12)

1. **Annuler un check-in déjà fait** : **OUI**. Les transitions arrière `COMPLETED → CONFIRMED` et `NO_SHOW → CONFIRMED` sont autorisées depuis cette page. Chaque retour arrière est **loggé obligatoirement** (auteur `userId`, statut précédent, statut nouveau, `timestamp`) via le logger applicatif. Justification : c'est un fix d'erreur opérationnelle jour-J (mauvais client scanné, no-show prononcé trop tôt). Garder ça en self-service évite un support ticket et un blocage encaveur.
2. **Sessions du même jour multiples** : tri **chronologique croissant** strict. La session "en cours" (i.e. `now ∈ [startsAt, endsAt]`) reçoit un badge **"En cours"** visuellement saillant. Justification : pas d'ambiguïté pour l'encaveur qui jongle entre plusieurs créneaux le même jour.
3. **Fenêtre de visibilité du bouton scan QR** : **H-2 avant la première session du jour → H+2 après la dernière session du jour**. Justification : couvre l'accueil anticipé (early birds) et les retardataires, sans laisser le bouton actif 24/24 (limite les erreurs de scan sur la mauvaise session).
