# ENC-127 — Action admin : suspension cave / utilisateur

## Objectif métier

Donner à Sam (admin) le pouvoir de **suspendre** une cave (`Winery.status = SUSPENDED`) ou un utilisateur (nouveau `User.status = SUSPENDED`) en cas de problème : fraude, comportement abusif, signalement non résolu, KYC retiré, demande judiciaire. C'est le levier de modération ultime, **réversible**, sans suppression définitive (qui passerait par ENC-135 droit à l'oubli). Indispensable pour ouvrir la plateforme au public sereinement.

## Acteurs

- **ADMIN** : Sam, exécute l'action.
- **WINEMAKER** suspendu : ne peut plus se connecter au dashboard encaveur ou ses expériences disparaissent du public.
- **CLIENT** suspendu : ne peut plus se connecter ni réserver.
- Clients ayant des bookings actives chez une cave suspendue : politique à confirmer (cf questions Sam).

## Préconditions & déclencheurs

**Préconditions** :

- Utilisateur connecté, rôle `ADMIN`.
- Cible (cave ou user) existe.
- Pour cave : `Winery.status` ∈ { `VERIFIED`, `PENDING` }. Pas de suspension de cave `REJECTED` (déjà out) ni déjà `SUSPENDED`.
- Pour user : `User.status` ≠ `SUSPENDED`.

**Déclencheurs** :

- Sam déclenche depuis le détail cave (`/admin/wineries/[slug]`) ou le détail user (`/admin/users/[id]` — à créer si pas existant).
- Sam déclenche depuis ENC-124 (liste expériences) → indirect : il suspend l'expérience, pas la cave.
- Demande judiciaire ou KYC Stripe révoqué (déclenché manuellement à ce stade, automatisable post-MVP).

## User stories

- En tant qu'admin, je veux suspendre une cave d'un clic + raison, pour la retirer immédiatement du public.
- En tant qu'admin, je veux suspendre un utilisateur (client ou encaveur) pour bloquer son accès à la plateforme.
- En tant qu'admin, je veux voir l'impact avant suspension : nb expériences publiées, nb bookings futures, etc.
- En tant qu'admin, je veux réactiver une cave/user suspendu (cas erreur ou problème résolu).
- En tant qu'encaveur suspendu, je veux savoir pourquoi (via email reçu) et qui contacter.
- En tant que client d'une cave suspendue, je veux savoir ce qu'il advient de ma résa (cf questions Sam).

## Critères d'acceptation (Gherkin)

```gherkin
Scénario : Suspendre une cave VERIFIED
  Étant donné une cave VERIFIED avec 3 expériences PUBLISHED et 8 bookings CONFIRMED futures
  Quand je clique "Suspendre cette cave" sur /admin/wineries/[slug]
  Et je saisis la raison "KYC Stripe révoqué"
  Et je confirme
  Alors Winery.status passe à SUSPENDED
  Et les 3 expériences disparaissent du listing public (filtre status winery + status experience dans queries publiques)
  Et l'encaveur ne peut plus se connecter au dashboard encaveur (redirect vers /suspended)
  Et un AdminAction est loggé (action = SUSPEND_WINERY, metadata.futureBookingsCount = 8)
  Et l'encaveur reçoit l'email "Ton compte EnCave a été suspendu"
  Et les 8 bookings futures restent CONFIRMED (politique par défaut, cf questions Sam)

Scénario : Réactiver une cave SUSPENDED
  Quand je clique "Réactiver"
  Et je saisis la raison "Problème KYC résolu"
  Alors Winery.status repasse à VERIFIED (sa valeur d'origine)
  Et les expériences PUBLISHED redeviennent visibles
  Et un AdminAction est loggé (action = UNSUSPEND_WINERY)

Scénario : Suspendre un utilisateur client
  Étant donné un user CLIENT avec 2 bookings futures
  Quand je le suspends avec raison "Comportement abusif signalé"
  Alors User.status passe à SUSPENDED
  Et ses sessions sont invalidées (Better Auth)
  Et il ne peut plus se connecter ni créer de booking
  Et ses bookings existantes restent telles quelles (politique par défaut)

Scénario : Suspendre un user qui est aussi encaveur
  Étant donné un user WINEMAKER lié à une cave VERIFIED
  Quand je suspends l'user
  Alors User.status = SUSPENDED
  Et la Winery liée passe AUSSI à SUSPENDED (cohérence)
  Et un seul AdminAction SUSPEND_USER est créé, avec metadata.linkedWinerySuspended = true

Scénario : Raison manquante
  Quand je tente de confirmer sans raison
  Alors le bouton reste désactivé + message "Une raison est obligatoire"
```

## Règles métier

- **Schema** :
  - `Winery.status` enum a déjà `SUSPENDED` (cf CLAUDE.md). OK.
  - **`User.status`** : à ajouter — enum `UserStatus { ACTIVE, SUSPENDED }`. Default `ACTIVE`. Migration Prisma.
- **Effet suspension cave** (`Winery.status = SUSPENDED`) :
  - Toutes les queries publiques (`/decouvrir`, page cave, page expérience) filtrent `winery.status === 'VERIFIED'`. À auditer dans le code existant (ENC-027 logique visibilité). Vérifier que `SUSPENDED` est bien exclu partout.
  - Encaveur suspendu : login Better Auth réussit (auth couche) mais middleware/layout encaveur redirige vers `/suspended` page d'info statique. Pas de modification dashboard.
  - Pas d'auto-annulation bookings (politique recommandée, cf questions).
  - Pas d'auto-refund.
  - Reverse possible : `SUSPENDED` → `VERIFIED` (restaure le statut d'avant suspension stocké dans `previousStatus` metadata d'AdminAction).
- **Effet suspension user** (`User.status = SUSPENDED`) :
  - Login Better Auth : on ajoute un check `user.status === 'ACTIVE'` au début du flow login, sinon erreur "Votre compte est suspendu, contactez support@encave.ch".
  - Sessions actives : invalider toutes les sessions Better Auth de cet user (cf API Better Auth).
  - Bookings existantes : conservées telles quelles.
  - **Cas spécial WINEMAKER** : suspendre un user WINEMAKER → suspendre **aussi** la cave liée (relation 1:1). Cohérence.
  - **Cas spécial CLIENT avec bookings** : conservation par défaut. L'encaveur honore la résa, l'expérience se déroule. Le client suspendu ne peut juste plus se logger / faire de nouvelle résa.
- **Réversion** :
  - Cave : `SUSPENDED` → `VERIFIED` (toujours, car on n'a suspendu que des `VERIFIED` ou `PENDING` et `PENDING` est rare). Stocker `previousStatus` dans AdminAction.metadata pour exactitude.
  - User : `SUSPENDED` → `ACTIVE`.
- **Raison obligatoire** : min 10 char, max 500. Stocké dans `AdminAction.reason`.
- **Notifications** :
  - Cave suspendue → email à l'encaveur.
  - User CLIENT suspendu → email au client.
  - Cave/User réactivé(e) → email "Tu peux à nouveau accéder à EnCave".
- **Cache** : invalider tags wineries + experiences (réutiliser `invalidateExperienceCaches` au niveau winery).
- **AdminAction** (ENC-126) : log systématique avec metadata.
- **Pas de cascade delete** : suspension n'efface rien.

## États UI

- **Loading** : spinner sur bouton suspension pendant la mutation (peut inclure invalidation sessions Better Auth, 1-2s).
- **Empty** : non applicable (action ponctuelle).
- **Error** :
  - Dialog reste ouverte si erreur serveur, toast destructive.
  - Raison < 10 char : erreur inline + bouton désactivé.
  - Cave déjà SUSPENDED (race condition) : toast "Cette cave est déjà suspendue", refresh.
- **Populated** :
  - Détail cave admin : badge "Suspendue" orange + bouton "Réactiver" (vert).
  - Détail user admin : badge "Suspendu" + bouton "Réactiver".
  - Page `/suspended` encaveur : page statique simple, brand EnCave, message d'info + email support.

## Cas limites

- **Suspendre une cave avec bookings PENDING_PAYMENT** : ces bookings expireront via cron ENC-067 → OK, pas de cas spécial.
- **Suspendre un user CLIENT avec bookings PENDING_PAYMENT** : ces bookings expireront. Pas d'action manuelle.
- **Suspendre un user pendant qu'il est en train de payer** : sa session est invalidée, son flow Stripe peut échouer. Acceptable (rare + intentionnel).
- **Désuspension partielle** : pas supportée. On désuspend tout d'un coup.
- **Cave SUSPENDED puis encaveur supprime son compte (nLPD)** : workflow nLPD prendra le pas (ENC-135), cave passe à une logique "anonymisée".
- **Tentative de connexion après suspension** : message clair affiché dans le formulaire login, pas de redirect silencieux.
- **Bookings déjà passées (COMPLETED)** : aucun impact.
- **Reconnexion de l'encaveur avec session encore valide** : le middleware doit revérifier `winery.status` à chaque requête sensible, pas seulement au login. Lourd ? Alternative : revalidate session lors de la suspension (Better Auth supporte ça).

## Hors-périmètre explicite

- Pas d'**auto-annulation des bookings futures** lors d'une suspension. Workflow séparé (ENC-128 pour refund au cas par cas).
- Pas de **suspension temporaire avec date de fin** (suspension manuelle, réactivation manuelle).
- Pas d'**escalade automatique** vers suspension (ex: 3 signalements → suspend). Pure décision admin.
- Pas de **bandeau public** "cave suspendue" sur les pages déjà indexées par Google (la page renvoie 404 ou page "indisponible", à trancher avec Léa — cohérent avec ENC-124).
- Pas de **suspension de l'admin** (Sam ne peut pas se suspendre lui-même — check côté serveur).
- Pas d'**API publique** pour suspension (purement interne).

## Métriques de succès

- Nombre de suspensions / mois (baseline).
- Délai moyen entre détection problème et suspension : < 1h.
- Taux de réactivation après suspension : indicateur qualité décisions.
