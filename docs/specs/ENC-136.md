# ENC-136 — Export données perso utilisateur en `.json` téléchargeable (nLPD)

## Objectif métier
Permettre à tout utilisateur (client ou encaveur) d'exercer son **droit à la portabilité / droit d'accès** au sens de la nLPD (art. 25 et 28). Concrètement : un bouton dans les settings qui génère un fichier `.json` contenant toutes les données personnelles que la plateforme détient sur lui. Doit être self-service (pas de ticket support à traiter manuellement) et idempotent. Couvre aussi le risque de demande légitime non honorée → sanction pénale.

## Acteurs
- **CLIENT** : déclenche l'export depuis `/settings/privacy/export`, télécharge un fichier `.json`.
- **WINEMAKER** : idem, avec en plus les données liées à sa winery (mais pas les PII des clients qui ont booké chez lui — RGPD/nLPD : ses clients ne sont pas ses données à exporter).
- **ADMIN** : peut déclencher pour un user à la demande (SAV) ; log dans `AdminAction`.
- **Système** : génère le JSON à la volée, signe l'URL temporaire, livre soit en download direct, soit par email (cf. règles).

## Préconditions & déclencheurs
- Utilisateur authentifié → page `/settings/privacy/export` → bouton "Exporter mes données" → server action → génération synchrone + download.
- Rate limit : **1 export par utilisateur toutes les 24h**, **3 par mois**. Au-delà, message "Vous avez déjà exporté vos données récemment. Réessayez dans X heures."
- Pas de re-saisie mot de passe (contrairement à ENC-135) : action moins destructive.

## User stories
- En tant que **client**, je peux récupérer en un clic tout ce qu'EnCave sait sur moi, au format machine-lisible.
- En tant que **encaveur**, je récupère mon profil + ma winery + mon historique commercial agrégé.
- En tant que **PO**, je peux prouver la conformité à un audit nLPD : la procédure existe, elle est documentée, elle marche.

## Règles métier
- **Format** : JSON UTF-8, indenté 2 espaces. Pas de CSV (incompatible avec la structure nested), pas de XML.
- **Périmètre du payload** :
  - `user` : tous les champs scalaires du modèle `User`, **sauf** le hash de mot de passe, les tokens, les `accountIds` OAuth (sécurité).
  - `bookings` : toutes les bookings (statut quelconque, y compris `CANCELLED_*`). Pas le `paymentIntentId` Stripe (secret de notre plomberie, pas une donnée perso utile au user). À débattre (cf. Questions).
  - `winery` (si winemaker) : champs publics + créneaux + experiences (métadonnées, pas les bookings entrantes).
  - `consents` : historique des consentements cookies, et `ageConfirmedAt` des bookings (pour audit personnel).
  - `messages` (post-MVP) / `reviews` (post-MVP) : à ajouter quand ils existeront.
- **Non inclus** :
  - PII d'autres utilisateurs (les bookings entrantes de la winery côté winemaker, par ex.).
  - Données techniques (logs Sentry, events PostHog) — orientation : on documente dans la privacy comment les obtenir via leur procédure dédiée.
  - Données Stripe (factures consolidées) — l'utilisateur les a déjà via les emails de confirmation + on peut pointer vers Stripe Customer Portal si on l'ouvre un jour.
- **Génération** : synchrone, server action, pas de queue. Volume estimé : <500 ko même pour un utilisateur chargé. Si on dépasse 10 Mo (cas extrême winemaker à 10k bookings), on passe en mode async + email avec lien signé (mais pas pour le MVP).
- **Livraison** : `Response` avec `Content-Type: application/json` + `Content-Disposition: attachment; filename="encave-export-<userId>-<YYYYMMDD>.json"`. Download direct.
- **Pas de mot de passe ni de lien temporaire signé pour MVP** : la session authentifiée fait l'accès. Le fichier est généré au moment de la requête, jamais stocké.
- **Rate limit** :
  - 1 export / 24h / user
  - 3 exports / 30 jours / user
  - Géré via Upstash Redis en prod (`src/lib/rate-limit.ts`), in-memory en dev.
- **Versioning du schéma** : `exportMetadata.version`. Toute évolution → bump version. Documenté dans la politique de confidentialité.
- **i18n** : les valeurs dans le JSON (statuts, titres) sont en **brut DB** (anglais : `CONFIRMED`, etc.) — c'est un export technique, pas un document marketing. On peut **localiser** la note d'explication intégrée (`exportMetadata.note`) en FR/DE/EN selon `locale`.
- **Audit** : log Pino structuré à chaque export. Optionnel : table `UserAction` ou `AdminAction` (si admin l'a déclenché) pour traçabilité.

## États UI
- **Loading** : bouton CTA en `pending` (spinner + texte "Génération en cours…"). Désactivé pendant la requête.
- **Empty** : aucune notion d'empty (le payload contient toujours `user`).
- **Error** :
  - Rate limit → toast info + texte sous le bouton avec le temps restant.
  - Erreur 500 → toast erreur générique + suggestion de retry / contact support.
- **Populated** : après succès → toast confirmation + déclenchement du download natif navigateur.

## Cas limites
- **User sans aucune booking** : payload `bookings: []`, pas un cas d'erreur.
- **User avec 1000+ bookings** (winemaker actif post-MVP) : volume estimé ~2 Mo, encore raisonnable. Si on dépasse 10 Mo un jour, basculer en mode async (post-MVP).
- **Bookings d'un user anonymisé qu'un winemaker exporte** : non concerné — un winemaker n'exporte pas les bookings entrantes (cf. règles métier).
- **Caractères spéciaux dans le nom (apostrophes, accents)** : JSON.stringify gère nativement.
- **Téléchargement interrompu** : pas grave, on peut relancer (mais respecter le rate limit).
- **Export concurrent (2 onglets ouverts, double-clic)** : la server action est idempotente côté DB (pas d'écriture). Le 2e appel passera ou sera rate-limité.
- **Tentative scrape via script** : rate limit protège. Token CSRF Next.js déjà en place pour server actions.
- **Locale fr-CH dates** : on garde ISO 8601 dans le JSON (`2026-05-11T14:30:00.000Z`), pas de formatage localisé — c'est de la donnée brute.

## Dépendances
- Server action `exportUserData` dans `src/server/actions/privacy.ts`.
- Query `getUserExportData(userId)` dans `src/server/queries/privacy.queries.ts` (assemble user + bookings + winery + consents).
- DTO/type `UserDataExport` dans `src/types/privacy.ts` (versionné).
- Rate limit : `src/lib/rate-limit.ts` (existe déjà, ajouter un bucket `data-export`).
- Logger : `logInfo('data_export', { ... })`.
- Politique de confidentialité (ENC-132b) doit décrire le format et le périmètre.

## Hors-périmètre explicite
- **Pas d'export CSV / XML / PDF** — JSON uniquement, format universel et nLPD-compliant.
- **Pas d'export asynchrone par email** au MVP (synchrone suffit, volumes raisonnables).
- **Pas d'export de données techniques** (Sentry, PostHog, logs Pino) — on documente la procédure manuelle.
- **Pas d'export des données détenues par nos sous-traitants** (Stripe Customer, Resend logs) — l'utilisateur doit s'adresser à eux directement.
- **Pas d'API publique** d'export (post-MVP, et seulement si demande).
- **Pas d'export multi-utilisateur** (admin qui exporterait plusieurs users d'un coup) — cas par cas, hors MVP.
- **Pas d'inclusion du `paymentIntentId` Stripe** au MVP — cf. Questions.

## Métriques de succès
- 100% des demandes traitées en <3s (génération + download).
- 0 PII tierce dans les exports (audit aléatoire de 5 exports).
- Compatibilité : le JSON s'ouvre sans erreur dans VS Code, navigateur, `jq`, Excel (avec parser JSON).

## ❓ Questions ouvertes pour Sam
1. **Inclusion `paymentIntentId` Stripe** dans `bookings[]` ? Pro : permet à un user technique de retrouver sa transaction côté Stripe. Contre : c'est un identifiant interne plomberie peu utile. Ma reco : non au MVP, oui si demande.
2. **Bouton "Demander un export complet via email"** pour récupérer aussi Sentry/PostHog/logs ? Reco MVP : juste un lien `mailto:privacy@encave.ch` sur la page, pas d'automatisation.
3. **Conservation des exports** : on ne stocke rien côté serveur (généré à la volée). OK ? Ma reco : oui, simple et sûr.
4. **Cas winemaker** : on lui donne (a) les métadonnées de ses experiences et (b) les bookings de ses experiences avec PII clients **anonymisées** (juste nb participants + date) ? Ma reco : (a) seulement, le (b) est un export commercial qui mérite une vraie page "Reversements/Statistiques" — déjà couvert par ENC-114.
5. **Notification email** après export ? Sécurité (genre "un export a été demandé sur votre compte") ou superflu ? Ma reco : oui, email léger de confirmation (anti-takeover).
