# ENC-126 — Table `AdminAction` + log automatique des actions admin sensibles

## Objectif métier

Tracer toutes les actions admin sensibles (refund manuel, suspension cave/user/expérience, validation cave, etc.) dans une table dédiée, pour : (1) audit & conformité nLPD, (2) reconstitution d'historique en cas de litige client/encaveur, (3) base pour le futur "AdminLog" UI consultable, (4) preuve de qui a fait quoi quand Sam aura un assistant admin. C'est l'infrastructure de traçabilité, transverse aux US 124/125/127/128.

## Acteurs

- **ADMIN** : auteur des actions logguées.
- Aucune action utilisateur direct. C'est de l'instrumentation back.

## Préconditions & déclencheurs

**Préconditions** :
- Schema Prisma updated avec le modèle `AdminAction` et son enum.
- Helper centralisé `logAdminAction()` dans `src/server/services/admin-action.service.ts`.

**Déclencheurs** :
- Toute server action admin sensible appelle `logAdminAction(...)` après la mutation principale, dans la même transaction Prisma quand possible.

## User stories

- En tant qu'admin, je veux que toutes mes actions sensibles soient automatiquement loggées sans que j'aie à m'en occuper.
- En tant qu'admin futur (post-MVP), je veux pouvoir consulter l'historique d'actions sur un objet (booking, cave, user) depuis son détail.
- En tant qu'EnCave (conformité), je veux pouvoir prouver qu'une action admin spécifique a été tracée (raison, auteur, timestamp, cible).

## Règles métier

- **Modèle Prisma** (proposition pour Jonas, à valider) :
  ```
  model AdminAction {
    id            String         @id @default(cuid())
    adminUserId   String
    adminUser     User           @relation(fields: [adminUserId], references: [id])
    action        AdminActionType
    targetType    AdminTargetType
    targetId      String
    reason        String         @db.Text
    metadata      Json?
    createdAt     DateTime       @default(now())
    
    @@index([targetType, targetId, createdAt])
    @@index([adminUserId, createdAt])
    @@index([action, createdAt])
  }
  
  enum AdminActionType {
    REFUND_BOOKING
    SUSPEND_WINERY
    UNSUSPEND_WINERY
    VERIFY_WINERY
    REJECT_WINERY
    SUSPEND_USER
    UNSUSPEND_USER
    SUSPEND_EXPERIENCE
    UNSUSPEND_EXPERIENCE
  }
  
  enum AdminTargetType {
    BOOKING
    WINERY
    USER
    EXPERIENCE
  }
  ```
- **Actions à logger en MVP** (liste exhaustive) :
  - `REFUND_BOOKING` (ENC-128) — succès ou échec.
  - `SUSPEND_WINERY` / `UNSUSPEND_WINERY` (ENC-127).
  - `SUSPEND_USER` / `UNSUSPEND_USER` (ENC-127).
  - `SUSPEND_EXPERIENCE` / `UNSUSPEND_EXPERIENCE` (ENC-124).
  - `VERIFY_WINERY` / `REJECT_WINERY` (action de validation cave existante — à rétrofiter dans le code existant).
- **Raison obligatoire** côté API : la fonction `logAdminAction()` refuse les `reason` vides ou < 10 caractères. (Sauf pour `VERIFY_WINERY` où la raison peut être facultative ou auto-générée "Validation manuelle".)
- **Metadata** : champ JSON libre par action. Conventions :
  - `REFUND_BOOKING` : `{ amountCents, refundId (Stripe), type: 'FULL' | 'PARTIAL', status: 'SUCCESS' | 'FAILED', errorCode? }`
  - `SUSPEND_*` : `{ previousStatus, futureBookingsCount? }`
  - `VERIFY_WINERY` : `{ previousStatus }`
- **Idempotence** : pas besoin d'unique constraint — on log même si la mutation principale échoue (avec status FAILED), c'est de l'audit. Mais en cas de retry idempotent côté Stripe, ne pas créer deux AdminAction → la responsabilité revient à la server action appelante (lock applicatif).
- **Transaction** : quand possible (mutation DB locale), wrapper l'action métier + `logAdminAction()` dans `prisma.$transaction([...])` pour atomicité. Pour les actions à effet externe (Stripe), logger après le call externe avec status approprié, hors transaction.
- **Helper service** (`src/server/services/admin-action.service.ts`) :
  ```ts
  export async function logAdminAction(params: {
    adminUserId: string;
    action: AdminActionType;
    targetType: AdminTargetType;
    targetId: string;
    reason: string;
    metadata?: Record<string, unknown>;
    tx?: Prisma.TransactionClient;
  }): Promise<AdminAction>
  ```
- **Query helper** :
  ```ts
  export async function getAdminActionsByTarget(
    targetType: AdminTargetType,
    targetId: string
  ): Promise<AdminAction[]>
  ```
  Utilisé par ENC-125 (section Historique) et future page audit.
- **Rétention** : pas de purge automatique. Logs conservés indéfiniment (cf nLPD : motif légitime d'intérêt + obligations comptables 10 ans pour les refunds).
- **Anonymisation user (ENC-135)** : si un admin user est supprimé (cas rare, mais Sam pourrait quitter), `adminUserId` reste pointé vers une ligne user anonymisée. La référence est conservée pour audit.
- **Pas d'écriture client-side** : `logAdminAction` est server-only, jamais appelée depuis un composant client.

## Cas limites

- **Mutation Stripe réussit mais write DB échoue** (cas rarissime, lock DB) : on log l'AdminAction avec metadata.status = 'INCONSISTENT' + on remonte un Sentry critical. Sam vérifie manuellement.
- **Migration Prisma sur une DB existante** : la table est créée vide. Pas besoin de back-fill (les actions admin passées — VERIFY_WINERY notamment — ne sont pas tracées rétrospectivement). On ajoute un commentaire dans la migration "Existing wineries verified before this date have no AdminAction log."
- **Multi-admin futur** : `adminUserId` permet de filtrer par admin. Aucune action à prendre maintenant.
- **Race condition sur same target** : ex: 2 onglets Sam, double-clic suspension. Le 2e log sera créé même si le statut est inchangé. Conséquence acceptable (= audit honnête). À documenter.
- **Metadata trop volumineuse** : limiter à 10 KB JSON max côté serveur (validation Zod). Au-delà : logger un warn + tronquer.

## Hors-périmètre explicite

- Pas d'**UI de consultation des logs** (page `/admin/audit`). Post-MVP. Pour MVP, accès via section Historique du détail booking (ENC-125) uniquement.
- Pas d'**export CSV** des logs.
- Pas de **logs pour les actions admin non sensibles** : consultation de pages, filtrage de listes, navigation. Seules les **mutations sensibles** sont loggées.
- Pas de **purge automatique** ni de **TTL**.
- Pas de **notification temps réel** (Slack/email) lors d'actions admin. Possibilité post-MVP.
- Pas de **signature cryptographique** des logs (anti-tampering). Le rôle ADMIN est de confiance pour MVP.
