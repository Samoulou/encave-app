# ENC-125 — Page admin liste réservations (recherche + détail)

## Objectif métier

Donner à Sam (admin) un outil de recherche transversal sur toutes les réservations de la plateforme, et une vue détail complète par booking. C'est la porte d'entrée du SAV : un client écrit "j'ai pas reçu mon QR pour la résa ENC-A4F2K9", Sam tape la référence, voit tout l'historique paiement / état / scan / refunds, et agit (refund manuel ENC-128, contact, etc.). Indispensable pour traiter les incidents en < 5 min.

## Acteurs

- **ADMIN** uniquement (Sam).
- Lecture seule sur les données client et encaveur (pas d'édition d'identité ici).

## Préconditions & déclencheurs

**Préconditions** :

- Utilisateur connecté, rôle `ADMIN`.
- Accès via `/admin/bookings` et `/admin/bookings/[reference]`.

**Déclencheurs** :

- Client écrit au support → Sam cherche par référence ou email.
- Encaveur signale un problème sur une résa → Sam cherche par nom de l'expérience ou cave.
- Audit ponctuel d'un événement.
- Click sur "nb bookings" depuis ENC-124 (drill-down).

## User stories

- En tant qu'admin, je veux rechercher une booking par référence `ENC-XXXXXX` directement.
- En tant qu'admin, je veux rechercher par email client ou nom du client.
- En tant qu'admin, je veux filtrer par statut, période d'événement, winery, expérience.
- En tant qu'admin, je veux voir un détail booking complet : client, encaveur, expérience, paiement, refunds, scans, historique d'état.
- En tant qu'admin, je veux atteindre depuis ce détail les actions SAV (refund manuel ENC-128, vue Stripe, contacter client/encaveur).

## Règles métier

- **Recherche unifiée** : un seul champ de recherche, plusieurs stratégies en parallèle :
  - Si l'input matche `/^ENC-[A-Z0-9]{6}$/i` → recherche exacte par référence.
  - Sinon → recherche `OR` sur `client.email` (contains), `client.firstName` + `client.lastName` (concat contains), `experience.title` (contains).
  - Normalisation Unicode (accents, casse).
- **Pagination** : 25 / page, tri défaut `createdAt DESC`.
- **Filtres** : statut booking, période d'événement (date du créneau), winery, expérience (déduit du filtre winery).
- **Détail sections** (ordre top-down) :
  1. **Réservation** : référence, statut + badge, date+heure créneau, nombre de personnes, total payé, montant refundé, date création.
  2. **Client** : nom complet, email, téléphone, lien vers profil admin (post-MVP), CTA mailto:.
  3. **Expérience & cave** : titre, lien vers page publique, nom cave, lien vers détail admin expérience (ENC-124), CTA mailto: encaveur.
  4. **Paiement** : montant payé, commission plateforme (12%), montant encaveur, statut Stripe, lien externe vers PaymentIntent dans dashboard Stripe, historique refunds.
  5. **Historique** : timeline AdminAction + transitions d'état booking + scan (checkedInAt).
- **Données sensibles** : email/tel client affichés sans masquage car Sam est admin. Pas de log d'accès à ce stade (post-MVP : `AdminAccess` table pour tracer les consultations).
- **Pas d'édition directe** : sur le détail, on ne modifie pas les champs booking. Les seules actions disponibles sont les server actions admin (refund — ENC-128).
- **Liens externes Stripe** : URL construite via `https://dashboard.stripe.com/payments/{paymentIntentId}` (avec/sans `/test/` selon env). Ouvre dans nouvel onglet.
- **Bookings anonymisées (nLPD ENC-135)** : si client supprimé, afficher `[Utilisateur anonymisé]` au lieu du nom. Email = `anonymized@encave.ch`. Référence + données financières restent visibles.
- **Performance** : query indexée sur `reference` (déjà unique), `clientId`, `experienceId`. Index composite à confirmer avec Jonas.

## États UI

- **Loading** : skeleton table sur liste, skeleton cards sur détail. Suspense par section.
- **Empty** :
  - Liste : `EmptyState` "Aucune réservation ne correspond" + bouton reset filtres.
  - Historique vide : section masquée (jamais vraiment vide, il y a toujours au moins la création).
  - Pas de refund : section masquée.
- **Error** : `error.tsx` segment-level + boundary par section détail. Si Stripe inaccessible pour l'historique paiement, on affiche les données DB + message "Détail Stripe temporairement indisponible".
- **Populated** :
  - Liste : table dense, badge statut coloré, référence en monospace (JetBrains Mono), montant aligné à droite.
  - Détail : 5 cards empilées (mobile) ou grid (desktop ≥ md). Sticky header avec référence + badge statut.

## Cas limites

- **Référence en minuscules** : `enc-a4f2k9` matche `ENC-A4F2K9`. Normalisation côté serveur.
- **Recherche très courte** (< 3 caractères) : on ne lance pas la recherche, on affiche un hint "Tape au moins 3 caractères".
- **Client supprimé / anonymisé** : référence + données financières restent visibles. Nom = "Utilisateur anonymisé".
- **Winery supprimée** : devrait être impossible en pratique (suspension only), mais si cas : afficher "[Cave supprimée]" et désactiver les CTA encaveur.
- **PaymentIntent Stripe introuvable** (cas rare, ex: nettoyage Stripe) : afficher "Réf Stripe introuvable" sans casser la page.
- **Très grand nombre de résultats** (>1000) : pagination tient. Recherche performante via index.
- **Filtre période sur événement futur lointain** : pas de limite supérieure, on liste tout.

## Dépendances

- **ENC-128** (refund manuel) : le bouton refund vit dans le détail booking ici. À livrer dans le même sprint.
- **ENC-126** (AdminAction) : la section "Historique" affiche les AdminAction liées à la booking.
- **ENC-124** : link depuis "Résa à venir" d'une expérience vers cette liste avec filtre experienceId.
- Aucun changement de schéma Prisma requis (lecture seule sur modèles existants).
- Recherche : utiliser Prisma `mode: 'insensitive'` (Postgres), pas besoin de full-text search à ce stade.

## Hors-périmètre explicite

- Pas d'**édition** des champs booking (nom, nb personnes, date créneau) depuis l'admin. Modification = annulation + nouvelle résa.
- Pas de **réémission du QR** depuis l'admin (post-MVP si besoin SAV récurrent).
- Pas de **renvoi de l'email de confirmation** (post-MVP, simple ajout futur).
- Pas d'**export CSV** des résultats.
- Pas de **statistiques agrégées** (CA, taux d'annulation) sur cette page — dashboard admin séparé post-MVP.
- Pas d'**audit log d'accès** (qui a consulté quelle booking) — post-MVP.
- Pas de **création de booking** depuis l'admin (pas de booking sur facture).

## Métriques de succès

- Temps moyen pour atteindre un détail booking depuis l'email d'un client : < 30s.
- Taux de tickets SAV résolus via cette interface (sans aller sur Stripe directement) : > 80%.
