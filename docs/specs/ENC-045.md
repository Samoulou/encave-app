# ENC-045 — Annulation événement par encaveur déclenche refund auto + emails

## Objectif métier
Quand un encaveur doit annuler une session (maladie, météo, force majeure), la plateforme doit gérer la rupture proprement : rembourser intégralement tous les clients confirmés, les notifier, et libérer le créneau. Sans cette automatisation, Sam doit traiter manuellement chaque cas — bloqueur opérationnel dès le 5e encaveur.

## Acteurs
- **WINEMAKER** : déclenche l'annulation d'une session ou d'un événement complet.
- **CLIENT** : reçoit la notification + refund automatique.
- **PLATEFORME (Stripe)** : exécute les refunds via Connect.
- **ADMIN** : visibilité dans les logs.

## Préconditions & déclencheurs
- Action explicite encaveur depuis la page détail événement (ENC-096) : bouton "Annuler cette session".
- Session avec au moins un `Booking` `CONFIRMED` ou `PENDING_PAYMENT`.
- Confirmation modale obligatoire (action destructrice irréversible).
- L'encaveur doit fournir un **motif** (libre, max 500 caractères) — visible dans l'email client.

## User stories
- En tant qu'**encaveur**, je dois pouvoir annuler une session en 3 clics et que mes clients soient remboursés et prévenus sans que j'aie à les contacter un par un.
- En tant que **client**, je veux être remboursé intégralement et savoir pourquoi quand un encaveur annule (pas de ma faute).
- En tant que **plateforme**, je veux que la commission 12 % soit aussi remboursée (commission n'est pas due si l'expérience n'a pas eu lieu).

## Critères d'acceptation (Gherkin)

```gherkin
Scénario : annulation d'une session avec bookings confirmés
  Étant donné une session "Dégustation du samedi" avec 3 bookings CONFIRMED et 1 booking PENDING_PAYMENT
  Quand l'encaveur clique "Annuler cette session", fournit le motif "Vendanges décalées" et confirme
  Alors les 3 bookings CONFIRMED passent en CANCELLED_BY_WINERY
  Et le booking PENDING_PAYMENT passe en CANCELLED_BY_WINERY (sa session Stripe est expirée best-effort)
  Et un refund Stripe full est créé pour chacun des 3 bookings CONFIRMED (montant total payé, commission incluse)
  Et 4 emails "Votre encaveur a dû annuler" partent aux 4 clients avec le motif
  Et la capacité de la session passe à 0 disponible (cancelled)
  Et la session est marquée cancelled (n'apparaît plus dans la recherche publique)

Scénario : refund Stripe sur paiement déjà capturé
  Étant donné un booking CONFIRMED avec paiement capturé (stripePaymentIntentId présent)
  Quand l'annulation se déclenche
  Alors stripe.refunds.create est appelé avec amount = total payé en cents et reverse_transfer = true
  Et l'identifiant du refund est persisté sur Booking.stripeRefundId
  Et la commission plateforme est récupérée via reverse_transfer

Scénario : booking PENDING_PAYMENT (pas de capture)
  Étant donné un booking PENDING_PAYMENT
  Quand l'annulation se déclenche
  Alors aucun refund n'est tenté
  Et la session Stripe Checkout est expirée via stripe.checkout.sessions.expire (best-effort, ignorer erreur)
  Et le booking passe en CANCELLED_BY_WINERY

Scénario : refund échoue côté Stripe
  Étant donné un refund qui retourne une erreur Stripe (ex : balance insuffisante)
  Quand le service rencontre l'erreur
  Alors le booking reste en CONFIRMED (pas de transition tant que refund pas réussi)
  Et un incident est créé : log error + Sentry + alerte Slack admin
  Et l'encaveur voit un toast "Un client n'a pas pu être remboursé automatiquement, l'équipe EnCave traite le cas"
  Et la session est tout de même marquée cancelled

Scénario : pas de bookings sur la session
  Étant donné une session sans aucun booking
  Quand l'encaveur l'annule
  Alors la session est marquée cancelled sans déclencher d'email ni de refund
  Et l'encaveur peut le faire sans modale de confirmation lourde (modale légère suffit)
```

## Règles métier
- **Refund policy spécifique** : annulation **par l'encaveur** = full refund **toujours**, indépendamment du délai (à la différence de l'annulation client où la règle >24h s'applique). Faute encaveur = client jamais lésé.
- **Commission** : la commission 12 % est **remboursée** au client (reverse_transfer Stripe). L'encaveur ne touche rien, EnCave ne touche rien.
- **Transition d'états** :
  - `CONFIRMED` → `CANCELLED_BY_WINERY`
  - `PENDING_PAYMENT` → `CANCELLED_BY_WINERY`
  - `COMPLETED`, `NO_SHOW`, autres `CANCELLED_*` : intouchables.
- **Ordre transactionnel** :
  1. Verrouille la session (status = `CANCELLING` en transaction Prisma — état transitoire).
  2. Pour chaque booking CONFIRMED : crée le refund Stripe.
  3. Pour chaque booking dont le refund a réussi : transition CANCELLED_BY_WINERY + persiste `stripeRefundId`.
  4. Pour chaque booking PENDING_PAYMENT : expire session Stripe + transition.
  5. Session → status `CANCELLED` + `cancellationReason` + `cancelledAt`.
  6. Envoi des emails (queue async via Resend, idempotent par bookingId).
- **Si un refund échoue** : on persiste l'échec sur le booking (`refundError`), on laisse en CONFIRMED, et un admin peut le traiter via ENC-128.
- **Limite anti-spam** : un encaveur ne peut pas annuler plus de **3 sessions par 7 jours glissants** sans intervention admin (signal de qualité — log warn si dépassé, pas de blocage hard en MVP).
- **Délai mini** : pas de délai minimum (l'encaveur peut annuler 1h avant — c'est nul pour le client mais c'est sa responsabilité, on documentera les CGU).
- **Audit** : log structuré `winery.session.cancelled` avec `sessionId`, `winerySlug`, `bookingsCount`, `totalRefundedCents`, `reason`.

## États UI
- **Loading** (pendant l'annulation) : bouton "Annulation en cours…" + spinner, formulaire bloqué.
- **Empty** : session sans bookings → modale allégée, pas de bloc "montant remboursé".
- **Error** : toast erreur + restauration de l'état UI ; les transitions réussies restent persistées (pas de rollback).
- **Populated** : session passée en `CANCELLED`, affichée avec badge rouge dans la liste, bookings affichés CANCELLED_BY_WINERY avec lien Stripe vers le refund.

## Cas limites
- Encaveur qui re-clique "Annuler" pendant que le job tourne : bouton désactivé + lock DB (statut `CANCELLING`).
- Booking annulé client juste avant (race) : status déjà `CANCELLED_BY_CLIENT` → skip dans la boucle.
- Session déjà passée (start < now) : interdit (bouton désactivé + error 400 si appel API direct).
- Session multi-créneaux (récurrent) : on annule **une occurrence** (un slot daté), pas tout le pattern d'AvailabilitySlot.
- Refund partiel impossible : Stripe peut refuser si le montant a été partiellement remboursé manuellement avant — fallback admin (ENC-128).
- Webhook `charge.refunded` qui arrive plus tard : doit être idempotent (cf. ENC-030b), pas de double transition.

## Dépendances
- ENC-030b (idempotence webhooks) **fortement recommandée** pour fiabiliser les retries.
- ENC-096 (page détail événement encaveur) : fournit le point d'entrée UI.
- ENC-128 (refund manuel admin) : filet de secours pour les échecs.
- Email Resend template `BookingCancelledByWineryEmail` (nouveau).
- Enum `SessionStatus` à étendre avec `CANCELLED` (si pas déjà présent) et état transitoire `CANCELLING` (à confirmer avec Jonas).
- Stripe Connect : `reverse_transfer: true` + `refund_application_fee: true` sur le refund.

## Hors-périmètre explicite
- **Pas de reschedule automatique** (proposer une autre date) — V2.
- **Pas de voucher / bon d'achat** en compensation — V2.
- **Pas d'annulation partielle** (annuler seulement certains bookings de la session) — la session entière passe.
- **Pas de notification SMS** — email uniquement.
- **Pas d'annulation d'une expérience entière** (status `ARCHIVED`) — c'est une autre action.

## Métriques de succès
- 100 % des bookings CONFIRMED d'une session annulée sont refundés en < 5 min.
- Taux d'échec refund < 1 %.
- 0 réclamation client "j'ai pas été remboursé" en sortie de cette feature.
